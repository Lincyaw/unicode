# 图模型

一个仓库在一个提交上的全部知识是一张图，称为该提交的**快照**。设计文件、代码和代码中的绑定是图的来源；追溯、索引、视图和分析都是这张图上的查询。本文定义图的统一结构、节点、边、记法、共有的属性、身份和版本，以及图必须满足的约束。设计文件的写法见 [format.md](format.md)，工具链如何建图和生成代码见 [design.md](design.md)。

## 1 统一结构

图由四样东西组成：

- **元素**：有名字、有边界的东西，构成一棵包含树。元素只有四个种类：`container`（边界）、`type`（数据的形状，可以带操作）、`op`（可调用的行为）和 `actor`（系统之外的参与者）。
- **关系**：元素之间带种类的边，例如包含、依赖、引用、继承、实现、调用和落实。
- **流程**：一组按次序组合的调用，可以带分支、可选、循环和错误处理。
- **性质**：关于元素或流程的一条可执行的陈述。它可以声明符号，用例用这些符号写成。

同一套种类用于两个抽象层：**设计层**是声明的意图，**代码层**是从代码抽取的事实。代码中的包和文件是 `container`，类和结构体是 `type`，函数和方法是 `op`。`realizes` 边把代码层的元素对到设计层中同一种类的元素上，两层因此可以逐个比较。

DDD、UML 类图、时序图、活动图和 C4 都是**记法**。一种记法从图中选取一部分，按自己的规则画出来；有的记法还给元素加上自己的标签，例如 DDD 的"聚合"。记法不增加结构，也不改变约束，见第 5 节。

此外，图中还有两类附加的节点：证据（M6）和评审记录（M7）。

## 2 来源

每个节点和每条边恰有一种**来源**：

- **声明**：设计文件写出的，或代码中的绑定写出的。
- **抽取**：语言后端从代码中静态读出的，不执行代码。
- **推导**：由其他节点和边按第 9 节的规则算出的。
- **运行**：执行检查时产生的。

声明是意图，抽取是事实，推导把二者连起来。第 10 节的约束比较意图与事实，结果写在声明项的状态上。

## 3 节点

每个节点有**种类**和**形式**：种类是下表中的一行，形式是该种类之下更具体的一类。

| 种类 | 设计层的形式 | 代码层的形式 | 属性 |
| --- | --- | --- | --- |
| `container` | `system`（根，恰有一个）、`component` | `package`、`file` | 名称、摘要、关注度、标签；设计层另有拥有的路径，代码层另有语言和路径 |
| `type` | `object`、`record`、`interface`、`enum`、`error` | 各语言的命名类型，例如 `class`、`struct`、`interface` | 名称、摘要、标签、字段、枚举值 |
| `op` | `op` | `func`、`method` | 名称、摘要、签名；代码层另有测试类别、是否为骨架 |
| `actor` | `person`、`external` | — | 名称、摘要 |
| `flow` | `flow` | — | 名称、摘要 |
| `step` | `call`、`alt`、`opt`、`loop`、`on` | — | 序号、分支标签、实参 |
| `property` | `invariant`、`postcondition`、`relation`、`transition` | — | 名称、陈述、符号、限定 |
| `case` | `declared` | — | 名称、摘要、每个符号的取值 |

- **设计层的 `type`**：`object` 有状态和行为，`record` 只有数据，`interface` 只有操作，`enum` 只有枚举值，`error` 可以出现在操作的 `raises` 中。
- **字段和枚举值**是 `type` 的属性，不是节点。字段的类型引用另一个 `type` 时，得到一条 `refers` 边。代码层只细到函数：变量和局部定义都不是节点。
- **`step`**：`call` 是一次调用；`alt`、`opt`、`loop` 是片段；`on` 是前一次调用抛出某个错误时的分支。片段包含步骤，所以一个流程的步骤构成一棵树。
- **`property`**：
  - 形式：`invariant` 对每个取值或状态成立；`postcondition` 在操作返回后成立；`relation` 在几次调用的结果之间成立，例如往返、幂等、变形关系；`transition` 要求状态只按允许的转移变化。
  - 符号：性质可以声明一组**符号**，每个符号有名称和设计中的类型，陈述对这些符号的每一组取值都成立。
  - 限定：缩小符号的取值范围，例如数值的区间、集合的大小、枚举的子集。
  - 一个符号的**取值域**是它的类型的全部取值，再按它的限定缩小。
- **`case`**：声明的用例为性质的每个符号给出一个具体的值，必须落在取值域之内。用例只给输入，不给期望结果；结果由性质的检查判断。
- **关注度**是设计层 `container` 的属性，取值为 `core`（核心）、`support`（支撑）或 `utility`（工具与基础服务）。它决定视图默认展开到哪里（[design.md](design.md) §7.2），不改变约束。
- **代码层的 `op`**：签名由语言后端归一化成与语言无关的形式（[design.md](design.md) §4）。测试类别是 `none`、`example`、`property` 或 `fuzz`，由后端按该语言的测试约定判定。是否为骨架，指函数体是否恰好是 `gen` 生成的未实现标记。

**证据**（M6）：`run` 是在一个提交上执行一组检查的一次运行；`result` 是一个检查在一次运行中的结论。运行中由生成器产生的输入和缩小后的反例也是 `case` 节点，形式为 `generated` 和 `counterexample`，来源为运行；反例可以转写成声明的用例。

**评审记录**（M7）：`review` 记下谁在哪个快照上评审了哪个节点或哪条边、当时它的摘要、结论和意见。评审记录不放在 Git 中，存放的位置在 M7 决定。

## 4 边

| 种类 | 从 → 到 | 来源 | 含义 |
| --- | --- | --- | --- |
| `contains` | container → container、type、op、flow、property；system → actor；type → op；flow → step；step → step；property → case | 声明；抽取 | 包含，每层各构成一棵树 |
| `uses` | container → container | 声明 | 允许的依赖 |
| `extends` | type → type | 声明；抽取 | 继承或嵌入 |
| `implements` | type → type | 声明；抽取 | 实现接口 |
| `refers` | type → type；op → type；property → type | 声明；抽取 | 字段、参数、返回值、错误或符号引用的类型 |
| `imports` | container → container | 抽取 | 文件导入包 |
| `calls` | op → op | 抽取 | 静态解析到的调用；属性中列出每个调用位置 |
| `calls` | step → op | 声明 | 步骤调用的操作；接收方是该操作所属的类型或容器 |
| `from` | step → actor、container、type | 声明 | 调用的发起方 |
| `handles` | step → type | 声明 | `on` 片段处理的错误 |
| `about` | property → container、type、op、flow | 声明 | 性质约束的对象 |
| `realizes` | 代码层 type → 设计层 type；代码层 op → 设计层 op | 声明（代码中的绑定）；推导 | 代码元素落实设计元素：类型和自由函数由绑定写出，方法由名称映射推出（第 9 节） |
| `checks` | 代码层 op → property、flow | 声明（代码中的绑定） | 这个函数执行该性质或流程的检查 |
| `owns` | 设计层 container → 代码层 file | 推导 | 文件归属的容器 |
| `depends` | 设计层 container → 设计层 container | 推导 | 实际的依赖 |
| `traces` | step → 代码层 op | 推导 | 落实该步骤所调用操作的函数 |
| `exercises` | 代码层 op → 代码层 op | 推导 | 检查函数沿静态调用可达的函数 |
| `reaches` | 代码层 op → 代码层 op | 推导 | 两个显著函数之间只经过细节函数的调用；属性列出经过的函数 |

## 5 记法与标签

记法分两类：

- **投影**只用结构，不需要标签。架构图画容器和依赖；UML 类图画类型、字段、操作及其关系；时序图按发起方和接收方分出生命线画流程；活动图按步骤的控制结构画同一个流程；调用图画函数之间的调用。同一个流程既可以画成时序图，也可以画成活动图。
- **带标签的记法**为元素加上记法自己的词汇，再按词汇选取和画出。

标签的词汇由工具链内置，是固定的。系统文件用 `notation` 声明项目使用哪些记法，元素只能带这些记法的标签；每个标签规定它能用在哪种元素上。第一版内置两套词汇：

| 记法 | 标签 | 用于 |
| --- | --- | --- |
| `ddd` | `bounded-context` | container |
| `ddd` | `aggregate`、`entity`、`value`、`domain-event`、`domain-service`、`repository`、`factory` | type |
| `c4` | `software-system`、`container`、`component` | container |

标签只影响视图，不影响约束。带标签的记法各有一个视图（[design.md](design.md) §7.1）。

## 6 共有属性

每个节点和每条边都有：

- **标识**：见第 7 节。
- **种类**、**形式**和**层**。
- **来源**：见第 2 节。
- **出处**：写出它的位置，即设计文件或代码文件的路径和行号；推导项的出处是推出它的那些边。
- **摘要**：它自身内容的 SHA-256，不含子节点，用来判断它变了没有。设计节点取它在规范格式下的声明文本；代码层的 `op` 取归一化后的签名和函数体；代码层的 `type` 取不含方法体的声明。
- **显著性**：显著，或是细节，见第 9 节。
- **状态**：只有声明项才有状态，取值为 `verified`（与代码一致）、`missing`（代码中没有对应项）、`stub`（对应的函数还是骨架）或 `contradicted`（代码与声明不符）。状态由第 10 节的约束算出。

## 7 身份

- **设计节点**的标识按包含关系逐段写出，段与段之间用 `.` 连接。例如：
  - 容器：`order`、`order.pricing`；
  - 类型：`order.Order`；
  - 操作：`order.Order.total`，容器直接提供的操作为 `order.parseCart`；
  - 流程和性质：`order.submit-order`、`order.total-is-sum`；
  - 用例：`order.total-is-sum.empty`；
  - 参与者：`customer`；
  - 步骤：流程的标识后接 `#` 和它在流程中按文本先后的序号，从 1 起，片段中的步骤也计入，例如 `order.submit-order#3`。
- **代码节点**的标识带语言前缀：包为 `go:github.com/x/shop/order`；类型为 `go:github.com/x/shop/order.Order`；方法为 `go:github.com/x/shop/order.Order.Total`；Python 的方法为 `py:shop.order.Order.total`；文件为 `file:src/shop/order.py`。
- **边**的标识是（种类，起点，终点）。同一对函数之间有多处调用时，只有一条 `calls` 边，调用位置都列在它的属性中。
- 改名或移动算作删除旧节点、新增新节点。工具可以提示可能的改名，但不会自动把两者认作同一个节点。

## 8 快照与比较

- 快照是一个提交或一个工作区的图。序列化的结果是确定的：节点和边按标识排序，相同的输入总是产生逐字节相同的输出。
- 比较两个快照时，按标识对齐节点和边，每一项归为新增、删除、修改（摘要不同）或不变。
- 评审状态由比较算出：一项从未审过，或审过之后摘要变了，就是待审。

## 9 推导规则

- **`owns`**：一个源文件归属于路径模式匹配它的设计层容器中最深的那个。
- **方法的 `realizes`**：代码层类型 c `realizes` 设计层类型 t 时，t 的每个操作 o 由 c 中名为 o 的名称映射（[design.md](design.md) §4）的方法落实，得到 `realizes` 边。`interface` 中声明的方法不是 `op` 节点；对接口，比较的是 c 的签名属性中的那一项。
- **`depends`**：容器 A 拥有的某个文件导入了容器 B 拥有其文件的包，或者 A 拥有的某个函数调用了 B 拥有的某个函数，且 A ≠ B 时，有 `depends` A → B。边的属性列出这些导入和调用，作为依据。
- **`traces`**：调用步骤 s `calls` 设计层操作 o，而代码层操作 f `realizes` o 时，有 `traces` s → f。
- **`exercises`**：从 `checks` 边的起点函数出发，沿 `calls` 能到达的每个函数 g，都有 `exercises` 边到 g。
- **显著性**：设计层的节点都是显著的。在代码层中，落实设计节点的类型和函数（包括按名称映射落实操作的方法）是显著的，带 `checks` 绑定的函数也是显著的，其余的类型和函数是细节；含有显著元素的文件和包是显著的；`gen` 产生的生成文件中的元素都是细节。人在设计中写下的就是他要关注的，所以显著性由设计决定，不需要另外标注。
- **`reaches`**：显著的函数 f 经由一个或多个细节函数调用到显著的函数 g 时，有 `reaches` f → g，属性列出每条这样的路径上经过的细节函数。f 直接调用 g 时只有 `calls`，没有 `reaches`。

## 10 约束

违反约束得到诊断。诊断一律是错误，没有警告。每条诊断都写明违反了哪条约束、在哪里、怎样修正。下文的容器、类型和操作，未注明层的都指设计层。

**设计内部**

1. 每个引用都能解析到声明的节点，种类与引用的位置相符。
2. 同一个父节点下，子节点的名称互不相同；参与者与顶层容器的名称也互不相同。
3. `contains` 构成一棵以 `system` 为根的树。
4. 调用步骤的发起方是参与者、容器或类型。被调用的操作所在的容器，或者就是发起方所在的容器，或者是它允许依赖的容器（第 11 条）。实参的个数等于操作的参数个数。
5. `on` 片段紧跟在一个调用步骤之后，它处理的错误在被调用操作的 `raises` 中。
6. 跨容器的类型引用（字段、参数、返回值、错误、`extends`、`implements`）也只能指向允许依赖的容器。
7. 元素的标签属于系统文件声明的记法，并且这个标签能用在这种元素上（第 5 节）。

**归属与依赖**

8. 每种已配置的语言，其源码根目录下的每个源文件都恰好归属于一个容器。
9. 互不嵌套的两个容器，路径模式不能匹配同一个文件。
10. 每条 `depends` A → B 都是允许的依赖，否则 `depends` 的状态为 `contradicted`。
11. A 可以依赖 B，当且仅当 B 是 A 的子容器，或者 A 或 A 的某个祖先 `uses` B。B 的子容器不随 B 一起被允许，要依赖它们须另写 `uses`。

**绑定**

12. 绑定指向存在的设计节点，种类相符：代码层类型的 `realizes` 只指向类型；不属于任何类型的代码层操作，其 `realizes` 只指向容器直接提供的操作；`checks` 只指向 `property` 或 `flow`。方法上不写 `realizes`。
13. 每个类型和每个操作恰好被一个代码层元素落实。没有时状态为 `missing`；落实操作的函数还是骨架时，状态为 `stub`。
14. 落实设计节点的代码元素，所在的文件归属于该设计节点所在的容器。
15. 代码元素的名称是它所落实的设计节点名称的映射，归一化后的签名与设计一致，否则状态为 `contradicted`。
16. 类型之间的 `implements` 和 `extends`，在落实它们的代码层类型之间也成立。

**可执行**

17. 每条 `property` 和每个 `flow` 至少有一个 `checks` 绑定。
18. 带 `checks` 绑定的函数，按它检查的对象分两种：
    - 检查一条声明了符号的性质时，它是一个**谓词**：除了语言要求的测试句柄（[design.md](design.md) §4），参数恰好是该性质的符号，按名称映射，类型一致。驱动由 `gen` 生成（第 23 条）。
    - 检查其余的性质和流程时，它本身是测试，测试类别为 `property` 或 `fuzz`。

    写死的具体例子写成声明的用例，不另写测试。
19. 每个调用步骤 s 都有 `traces` s → f。发起方是类型时，落实该类型的代码层类型中，要有某个方法沿 `calls` 能到达 f；发起方是容器时，该容器拥有的某个函数要能到达 f；否则 s 的状态为 `missing`。发起方是参与者时不检查调用。调用的先后顺序由流程的检查在运行时核对（M6）。

**符号与用例**

20. 符号的类型必须能够生成：它不是 `interface` 或 `error`，也不经由必填字段递归引用自身。
21. 限定的路径从一个符号出发，沿字段逐段解析；经过 `list`、`set`、`map` 时，作用于每个元素或值。区间只用于 `int` 和 `float`，枚举子集只用于 `enum`，大小只用于 `list`、`set`、`map`、`string` 和 `bytes`。
22. 用例为性质的每个符号恰好给出一个值。值必须符合符号的类型：记录给出全部字段，枚举值存在，只有 `optional` 才能取 `none`。值还必须满足该性质的全部限定。

**生成**

23. 每个生成文件（生成器和驱动，[design.md](design.md) §6）都与 `unicode gen` 按当前的设计产生的内容逐字节相同。
