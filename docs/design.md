# unicode 工具链设计

unicode 把一个仓库的设计意图、代码和证据组织成一张图（[model.md](model.md)），设计意图写在设计文件中（[format.md](format.md)）。本文写工具链本身：用法、组件、语言后端、建图、生成、视图与切片、命令行、计划，以及工具链对自己的验证。设计理由集中在附录 A，待定的事项列在附录 B。

## 1 目标

- **管理人的上下文**：人只看核心，也就是架构、流程、核心函数，以及每条性质和它的证据；细节在点开时才出现。
- **知识与代码一致**：结构从代码静态抽取，意图由设计声明，二者由检查对齐。没有对齐的知识会明确标出来。
- **设计先行**：先写设计，按设计生成骨架、生成器和测试驱动，再写函数体和谓词。
- **结构统一，记法可换**：图只有一套结构（[model.md](model.md) §1），DDD、UML、时序图、C4 都是它的视图。

## 2 使用方式

工具链的使用者是设计者兼评审者，可以是人，也可以是 Claude Code 的主会话。实现由设计者派给 agent 完成。一轮工作分五步：

1. 设计者编写或修改设计文件：组件、类型、流程，以及带符号和用例的性质，直到 `unicode check --design-only` 通过。
2. 设计者运行 `unicode gen`，为缺少的设计节点生成骨架，并重写生成器和测试驱动。
3. 设计者把要实现的设计节点派给 agent，任务附上这些节点的切片（`unicode slice`，§7.3）。
4. agent 写函数体和谓词，自己运行 `unicode check` 和测试，然后交回。
5. 设计者用 `unicode check`、`unicode diff` 和视图评审交回的结果。通过就合入；不通过就带着诊断再派一次。

工具链不调度 agent，也不保存任务。它只提供设计、生成、检查和查询四类能力。

## 3 组件

工具链是一个 Go 程序，module 为 `github.com/lincyaw/unicode`，命令为 `unicode`。每个包是一个组件，M1 时写进工具链自己的设计文件。

| 包 | 职责 | 依赖 |
| --- | --- | --- |
| `internal/diag` | 诊断：位置、诊断码、原因与修正 | — |
| `internal/graph` | 图的类型、合并、推导、摘要、序列化和比较 | diag |
| `internal/syntax` | 设计文件的词法、语法、语法树和规范格式的打印 | diag |
| `internal/design` | 把语法树解析成设计层的节点和边；检查设计内部、符号与用例的约束 | syntax、graph、diag |
| `internal/lang` | 语言后端的接口、名称映射和生成计划的类型 | graph、diag |
| `internal/lang/golang` | Go 后端 | lang、graph、diag |
| `internal/lang/python` | Python 后端，嵌入抽取脚本 | lang、graph、diag |
| `internal/check` | 归属、依赖、绑定、可执行和生成这几组约束 | graph、diag |
| `internal/query` | 节点、引用、搜索、切片和影响 | graph |
| `internal/view` | 视图的选取与折叠 | graph |
| `internal/gen` | 生成计划：缺少的骨架，以及应有的生成文件 | graph、lang、diag |
| `cmd/unicode` | 解析参数，调用其余组件，输出结果和退出码 | 全部 |
| `python/uc` | Python 运行时包 `uc`（装饰器），随工具链发布 | — |

`graph` 在最底层：设计层由 `design` 写入图，代码层由语言后端写入图，其余组件只读图。

## 4 语言后端

每种语言有一个后端，实现以下接口（草案）：

```go
type Backend interface {
	Language() string                                    // "go"、"python"
	Extract(root string, srcRoots []string) (graph.Fragment, []diag.Diagnostic, error)
	MapName(kind graph.Kind, designName string) string   // 名称映射
	Generate(plan Plan) ([]Edit, error)                  // 骨架只新增；生成文件整体重写
}
```

- **抽取**：后端读出 `container`、`type`、`op` 节点，以及 `contains`、`imports`、`calls`、`refers`、`extends`、`implements` 边。它同时读出代码中的绑定，写成 `realizes` 和 `checks` 边；绑定的写法不合格式时，给出诊断。后端产出的是代码层的图片段，格式与快照相同。
- **Go 后端**：在进程内用 `golang.org/x/tools/go/packages` 和 `go/types` 解析源码和类型。调用按静态类型解析，接口方法的调用解析到接口的方法。
- **Python 后端**：工具链内嵌一个只用标准库的抽取脚本，以 `python3 -I` 运行。脚本用 `ast` 解析源码，把图片段以 JSON 写到标准输出。调用按名称和导入关系解析，解析不到的调用不成边，只计数。生成在 Go 中按模板完成。
- **测试类别**：Go 中，`func FuzzX(f *testing.F)` 为 `fuzz`，调用了 `rapid.Check` 的 `TestX` 为 `property`，其余 `TestX` 为 `example`。Python 中，带 `hypothesis.given` 的测试为 `property`，用 `atheris` 的为 `fuzz`。
- **名称映射**：

  | 设计 | Go | Python |
  | --- | --- | --- |
  | 类型 `Order` | `Order` | `Order` |
  | 操作 `unitPrice` | 方法或函数 `UnitPrice` | `unit_price` |
  | 字段 `unitPrice` | 字段 `UnitPrice` | 属性 `unit_price` |
  | 枚举值 `draft` | 常量 `OrderStatusDraft` | 成员 `DRAFT` |
  | 性质 `total-is-sum` 的谓词 | `checkTotalIsSum` | `check_total_is_sum` |
  | 流程 `submit-order` 的测试 | `TestFlowSubmitOrder` | `test_flow_submit_order` |

- **谓词的签名**：参数依次是该性质的符号，按名称映射，类型一致。Go 的谓词另有第一个参数作为测试句柄，类型为 `rapid.TB`；Python 的谓词没有测试句柄，用 `assert` 断言。
- **类型映射**：归一化签名用设计的类型写法，各语言的写法与它一一对应。例如 `int` 对应 Go 的 `int` 和 Python 的 `int`；`list<T>` 对应 `[]T` 和 `list[T]`；`optional<T>` 对应 `*T` 和 `T | None`。在 Go 中，`raises` 对应最后一个返回值 `error`；在 Python 中，错误不出现在签名里。Python 中落实设计节点的函数和谓词，每个参数和返回值都必须有类型标注。

## 5 建图

1. `syntax` 解析 `design/` 下的全部设计文件，`design` 把它们解析成设计层的节点和边，并检查用例的值是否符合符号的类型和限定。
2. 每种已配置的语言，由它的后端抽取源码根目录下的代码。
3. `graph` 合并设计层和代码层，再按 [model.md](model.md) §9 推导出 `owns`、方法的 `realizes`、`depends`、`traces`、`exercises`、显著性和 `reaches`。
4. `check` 检查 [model.md](model.md) §10 的约束，把结果写成诊断和声明项的状态。
5. `build` 把快照写到 `.unicode/graph.json`，搜索索引写到 `.unicode/index.json`。`.unicode/` 不进 Git。

相同的输入总是得到逐字节相同的输出。M3 起，抽取结果按文件缓存，键为文件的摘要和后端的版本，只重新抽取变了的文件。

## 6 生成

`unicode gen` 产生两类文件。

**骨架**只在缺少时生成一次，之后归人或 agent 所有。`gen` 只新增，从不改写已有的代码元素。它为以下各项生成骨架：

- 每个没有落实的类型：带 `realizes` 绑定的类型，字段和操作按名称映射，方法体是未实现标记。
- 每个没有落实的、组件直接提供的操作：带 `realizes` 绑定的自由函数。
- 每条没有检查的性质：声明了符号时，生成带 `checks` 绑定的谓词，参数是这些符号；没有声明符号时，生成带 `checks` 绑定的性质测试。
- 每个没有检查的流程：带 `checks` 绑定的测试，函数体按步骤的次序列出要调用的操作。

**生成文件**归 `gen` 所有，每次运行都按当前的设计整体重写，人不编辑。文件开头标明它是生成文件。`unicode check` 确认它们与 `gen` 的输出逐字节相同（[model.md](model.md) §10 第 23 条）。每条声明了符号的性质，有以下生成文件：

- **生成器**：每个符号一个，按它的类型递归构造：
  - 内置类型取该语言的生成器，区间和大小作为边界；
  - `record` 和 `object` 由各字段的生成器组合而成；
  - `enum` 从枚举值或限定的子集中取；
  - `list`、`set`、`map` 按大小的限定生成；
  - `optional` 在 `none` 和 T 的值之间取。

  符号的取值域（[model.md](model.md) §3）因此只写在设计中一处，生成器和用例的检查都由它推出。
- **驱动**：有三个，都把输入交给同一个谓词：
  - 性质测试：由生成器产生输入，失败时把输入缩小到最小的反例；
  - fuzz 目标：把 fuzz 引擎给出的字节解码成各符号的取值；
  - 用例回放：把每个声明的用例转写成该语言的值，逐个交给谓词。
- **语言的对应**：Go 中，生成器用 `rapid.Custom` 构造，性质测试用 `rapid.Check`，fuzz 目标是 `FuzzX` 中的 `rapid.MakeFuzz`，用例回放是普通的 `TestX`。Python 中，生成器是 Hypothesis 的 strategy，性质测试用 `@given`，fuzz 目标用 Hypothesis 的 `fuzz_one_input` 接到 atheris 上，用例回放逐个调用谓词。生成文件放在哪里由后端决定，M4 时定下。

## 7 视图、切片与查询

### 7.1 视图

视图由三部分组成：从图中选取哪些节点和边、默认怎样折叠、元素按什么次序排列。视图只给出结构，不给出坐标，布局由前端完成。

**投影**只用结构，对任何项目都可用：

| 视图 | 输入 | 选取 |
| --- | --- | --- |
| 架构 `architecture` | 容器，缺省为整个系统 | 子容器、`uses`、`depends` 及其状态 |
| 类 `class` | 容器或类型 | 类型及其字段和操作、类型之间的边；可以在设计层和代码层之间切换 |
| 时序 `sequence` | 流程 | 步骤树、按首次出现排列的生命线、每一步的 `traces` 和状态 |
| 活动 `activity` | 流程 | 同一个步骤树，按控制结构画出 |
| 调用 `calls` | 操作或函数 | 显著函数之间的 `calls` 和 `reaches` |
| 性质 `property` | 性质或容器 | 性质、`about`、符号、限定、用例、谓词和驱动；M6 起加上结果、生成的用例和反例 |
| 代码 `code` | 文件或类型 | `contains`，以及进出的调用 |

**带标签的记法**只在系统文件声明了该记法时可用：

| 视图 | 输入 | 选取 |
| --- | --- | --- |
| DDD `ddd` | 容器 | 带 `bounded-context` 的容器，其中带 DDD 标签的类型，以及它们之间的 `refers`、`extends`、`implements` |
| C4 `c4` | 容器 | 按 C4 的标签分层：软件系统、容器、组件，以及它们之间的依赖 |

时序视图和调用视图合起来回答"这个流程怎样走、经过哪些核心函数"。

### 7.2 折叠与展开

视图默认只显示显著的节点（[model.md](model.md) §9），并按容器的关注度折叠：

- `core` 的容器展开。
- `support` 的容器折叠成一个节点，只显示名称、摘要和进出它的依赖。
- `utility` 的容器不画出来，指向它的依赖也不画，视图边上只给出"另有 n 个工具与基础服务"。
- 细节函数不显示。显著函数之间经过细节函数的调用，画成一条 `reaches` 边，标明经过了几个细节函数。

视图的输入 `expand` 列出要展开的标识：

- 展开一个折叠的或未画出的容器，显示它的内容；
- 展开一条 `reaches` 边，显示路径上经过的细节函数；
- 展开一个显著函数，显示它直接调用的细节函数。

展开的状态只存在于视图的输入里，工具链不保存它；前端把它写在页面地址中。

### 7.3 切片

切片是回答一个问题所需的最小上下文。人在详情中看到的，和派给 agent 的任务所附的，是同一种切片。一组节点 N 的切片包含：

- N 中每个节点的完整声明、状态和出处；
- 每个节点到 `system` 的祖先链，只给摘要；
- 每个节点沿各种边一步可达的显著节点，只给摘要；细节节点只给个数，展开之后才列出；
- 按种类补充的内容：
  - 操作：所属类型的字段和各操作的签名、约束它的性质、调用它的流程步骤、落实它的函数的位置；
  - 性质：它约束的对象的签名、各符号的类型及其字段、限定、用例，以及谓词的位置；
  - 流程：步骤树和每一步的 `traces`；
  - 容器：子容器、`uses`、带状态的 `depends`，以及类型的摘要。

代码只给位置（路径和行号）；加 `--with-code` 时附上源码。

### 7.4 影响与索引

- **影响**：对一组变更的节点 C，影响是沿 `calls`、`reaches`、`refers`、`realizes`、`traces`、`exercises`、`depends`、`about`、`checks` 反向能到达 C 的节点。结果按种类分组，每一项附上一条最短的路径，说明它为什么受影响。默认只列显著的节点。
- **索引**：可以按标识、名称、种类和摘要文字查找节点，并按边反查，例如谁调用了它、哪些性质约束它。

## 8 命令行

命令行的使用者既是人，也是 agent，约定遵守 cli-design 的规则：标准输出只放数据，诊断和日志写到标准错误；每个命令都支持 `--format text|json`；不读标准输入，不提示确认。

| 命令 | 作用 | 写入 |
| --- | --- | --- |
| `unicode fmt [--check] [path...]` | 把设计文件改写成规范格式；带 `--check` 时只报告，不改写 | 设计文件 |
| `unicode check [--design-only]` | 建图，检查全部约束，输出诊断 | 无 |
| `unicode build [--out DIR]` | 建图，写出快照和索引 | `.unicode/` |
| `unicode gen [--dry-run]` | 生成缺少的骨架，重写生成文件 | 新的代码元素和生成文件 |
| `unicode diff <rev> [<rev>]` | 比较两个快照；只给一个版本时，与工作区比较 | 无 |
| `unicode node get <id>` | 给出一个节点及其边 | 无 |
| `unicode node search <text> [--kind K]` | 按名称和摘要搜索 | 无 |
| `unicode node refs <id>` | 给出指向它的边 | 无 |
| `unicode slice <id>... [--expand ID]... [--with-code]` | 切片 | 无 |
| `unicode impact <id>...` | 影响 | 无 |
| `unicode view <kind> <id> [--expand ID]...` | 视图的数据 | 无 |
| `unicode schema` | 输出命令、参数和各命令输出的 JSON Schema | 无 |

- **全局参数**：`--root DIR` 指定仓库根目录，缺省为向上找到的第一个含 `design/system.uc` 的目录；`--rev REV` 让查询读一个提交的快照，缺省读工作区。
- **退出码**：0 成功；1 未知错误；2 参数错误；3 标识不存在；5 冲突（`gen` 要写的位置已有不同的内容）；7 环境错误（找不到 `python3` 或 Go 工具链）；10 存在诊断。
- **诊断的 JSON**：`{code, subject, path, line, column, message, fix}`。`code` 是稳定的诊断码，每条约束一个，M1 时与约束一起定义。

## 9 计划

| 里程碑 | 内容 | 完成的标志 |
| --- | --- | --- |
| M0 设计 | 本文、[model.md](model.md)、[format.md](format.md) | 设计评审通过 |

| M2 Go 后端 | 抽取、绑定、建图、全部约束 | 工具链的代码带上绑定，`unicode check` 在工具链自身上通过 |
| M3 查询与视图 | `node`、`slice`、`impact`、`view`、`build` 和抽取缓存；查看器的雏形 | 此后给 agent 派任务都附上切片 |
| M4 Go 生成 | `gen`：骨架、生成器和三个驱动 | 此后工具链的新组件和性质检查都由 `gen` 起头 |
| M5 Python | 抽取脚本、`uc` 包、Python 的生成；把 [format.md](format.md) §5 的商店例子做成样例仓库 | 样例仓库通过 `unicode check`，驱动能跑 |
| M6 证据 | 读入测试和 fuzz 的结果、生成的用例和反例；反例可以转写成声明的用例；在运行时核对流程的调用顺序 | 性质视图显示证据 |
| M7 评审 | 评审记录与评审状态，按比较结果评审 | 评审只列出待审的项 |

从 M1 起，工具链用自己的格式描述自己；从 M2 起，用自己检查自己。M1 写出工具链的设计之后，本文、[model.md](model.md) 和 [format.md](format.md) 中能写成性质的条目，都移到设计文件里成为 `property`，文档只留下理由和设计文件表达不了的内容。

## 10 工具链对自己的验证

- **静态检查**：`gofmt`、`go vet`、`golangci-lint`，以及 `unicode fmt --check` 和 `unicode check`。M2 之前，组件之间的导入边界由 golangci-lint 的 depguard 检查；M2 起改由 `unicode check` 按设计中的 `uses` 检查。
- **性质**（M1 时写成带符号的 `property`，M4 起由工具链自己生成驱动）：
  1. `fmt` 幂等。
  2. 规范格式打印之后再解析，得到同一棵语法树。
  3. 解析任何字节都不会 panic；出错时给出带位置的诊断。
  4. 相同的输入得到逐字节相同的快照，与文件的枚举顺序无关。
  5. 诊断的集合与文件的枚举顺序无关。
  6. `gen` 对骨架只新增：`gen` 之前已有的每个函数体，`gen` 之后逐字节不变；`gen` 两次与一次的结果相同；`gen` 之后不再有 `missing`，只剩 `stub`。
  7. 生成器产生的每个值，都通过与声明的用例相同的类型和限定检查。
  8. `diff(a, a)` 为空；`diff(a, b)` 与 `diff(b, a)` 互为相反。
  9. 推导出的 `depends`、`traces`、`reaches` 与按 [model.md](model.md) §9 的定义直接计算的结果相同；输入是随机生成的小图。
- M4 之前，这些性质的驱动手写，用 `pgregory.net/rapid` 和 Go 原生的 fuzz。具体的例子作为用例或种子，不另写固定例子的测试。

## 附录 A 设计理由

1. **一套结构，多种记法**：DDD、UML、时序图各自的元素，都能归为容器、类型、操作、参与者、流程和性质。把它们统一成一套结构，同一个对象在各种图中自然就是同一个节点；换一种记法只是换一种视图，不用改设计。
2. **两层用同一套种类**：代码层的包、类型和函数，与设计层的容器、类型和操作种类相同。`realizes` 因此是同种类节点之间的对应，比较和视图都可以在两层之间切换。
3. **自定义格式，而不是 YAML 或 JSON**：签名、流程的步骤和限定各写成一行；只有一种规范写法，diff 干净；语法错误能精确到位置，并说明怎样修正；不接受别的写法，校验才有意义。
4. **只有错误，没有警告**：警告会被忽略。只要有一处违反留下来，agent 就会把它当成惯例去复制。
5. **代码只细到函数**：字段和变量太多，人记不住，设计也不需要一一对应到它们。
6. **绑定只写在类型和自由函数上**：方法按固定的名称映射对应到操作，不必在每个方法上再写一遍标识；生成和检查都按同一套映射进行。
7. **静态抽取**：不运行代码就能建图，又快又确定，也不需要运行环境。运行时的证据作为证据节点，在 M6 单独加入。
8. **显著性由设计决定**：人写进设计的就是他要关注的。不另设一套标注，就不会出现标注与设计不一致。关注度只用来把整个支撑容器或工具容器折叠起来。
9. **取值域只写一处**：符号的类型和限定写在设计中，生成器、fuzz 的解码和用例的检查都由它推出。用例只给输入，结果由谓词判断，所以用例是性质的实例，而不是另一份测试。
10. **骨架与生成文件分开**：骨架生成之后归人所有，`gen` 不改写它，人写的函数体因此不会丢失；生成器和驱动完全由设计决定，归 `gen` 所有，每次重写，并由检查确认与设计一致。
11. **先做 Go 后端**：工具链用 Go 写，Go 后端做好后，工具链立刻能检查自己，每一步都有真实的反馈。
12. **快照不进 Git**：快照是生成物，随时可以从提交重建；Git 只保存设计文件和代码。
13. **工具链不调度 agent**：调度由使用工具链的设计者负责。工具链只做设计、生成、检查和查询，接口因此简单而确定。

## 附录 B 待定

1. Python 抽取脚本输出的格式与快照共用一份 schema。schema 用什么语言写：直接手写 JSON Schema，还是用 TypeSpec 生成。
2. 流程中的领域事件：发布和处理事件（异步消息）怎样写。
3. 错误的完整性：是否要求一次调用可能抛出的每个错误，要么有 `on` 分支处理，要么出现在发起方操作的 `raises` 中。
4. 流程中调用外部系统（`external` 参与者）怎样写。
5. `relation` 和 `transition` 性质往往涉及一串操作。这串操作是写成一个命令列表类型的符号（例如 `forall ops: list<Command>`），还是另加一种状态机的写法。
6. 限定的写法是否还需要字段之间的关系，例如 `start <= end`；M1 只支持区间、大小和枚举子集。
7. 评审记录存放在哪里（M7）。
8. 查看器用什么前端栈。
9. 通用的 Go 规则放进 engineering-conventions skill 的 `reference/go.md`；本仓库的 AGENTS.md 只留本仓库特有的规则。
10. 设计中的泛型类型（类型参数）：M1 不支持。
11. [model.md](model.md) §10 第 18 条（检查必须是谓词，或是性质测试、fuzz）是否对所有项目强制。
12. 记法的词汇是否允许项目扩展。目前内置、固定，以保证校验。
