# CLAUDE.md

This project's engineering conventions are the general rules of the `engineering-conventions` skill, with the rules of this file on top. Load that skill before writing, refactoring or reviewing code, designing components or interfaces, writing verification, or editing documents. `AGENTS.md` is a symlink to this file, so Codex reads the same rules.

## Project

- unicode is a toolchain that builds one graph of a repository's design intent, code and evidence; notations (DDD, UML class and sequence diagrams, activity diagrams, event storming, C4) are views of that graph. `docs/model.md` defines the graph, `docs/language.md` the design language (its files, lexis, grammar, semantics and compilation) and the code bindings, and `docs/design.md` the toolchain itself. `docs/decisions.md` logs each decision and its reason.
- The toolchain's own design is in `design/*.uc`, written in its own format. Each Go package is one component there, and code element names follow the design through the name mapping of `docs/design.md` §4.

## Principles

1. **Design first.** A change to the graph, the format or the toolchain's structure edits the documents and the design files before any code. The documents state the current design; `docs/decisions.md` records only what was decided and why.
2. **Requirements are found by using the toolchain on itself.** When the toolchain's own design cannot say something it needs, the model or the format changes (with a decision entry); the design file and the code never work around the gap. Code is never reshaped to suit a blind spot of the toolchain (for example, calling a function directly only so that the extractor sees the call); the toolchain is extended instead.
3. **The specification decides, not the implementer.** Where `docs/model.md` or `docs/language.md` is ambiguous, the implementer picks the reading closest to the text, states the ambiguity and the reading in its report, and the main session fixes the document.
4. **Strict by construction.** Every diagnostic is an error: there are no warnings. Each one carries a stable code (`<component>.<kebab-name>`), a position, the cause and the fix. Nothing is suppressed without a one-line reason, and every suppression is listed in review.
5. **Every check is a predicate, and a property states its claim as expressions.** Each property and flow has exactly one predicate whose parameters are its symbols. A property or flow writes its claim as `ensure` expressions over the declared types, and a time budget as `within` (docs/language.md §4.4); `unicode gen` turns them into its predicate (M4). A claim that cannot be written as expressions is first split into atomic properties; what still cannot is declared `manual` with its reason, gets a hand-written predicate, and is reviewed on every change. A property's or flow's summary states exactly what its predicate checks, and a generated symbol's domain description exactly what its bound generator draws; a change to either side changes the other (docs/language.md §4.2). The language stays at the level of abstract declarations: the expression language keeps only what stating relations needs (its one builtin is `size`), and no builtin or helper operation is added to make one property expressible; any new construct needs a decision entry. Tests are only the drivers that call predicates. Until `unicode gen` writes drivers (M4), they are written by hand in `*_test.go` with `pgregory.net/rapid` and native fuzzing, and are deleted when generation replaces them. No test pins one example; concrete examples are declared cases.
6. **Bindings from the first line.** Code that realizes a design node carries its `//uc:realizes` directive, predicates carry `//uc:checks`, generators of generated symbols carry `//uc:generates`, even before the checks that read them exist.
7. **The toolchain speaks English; the documents are Chinese.** Diagnostics, help text, CLI messages, identifiers, code comments, test messages and commit messages are English, so library messages (participle, cobra, pflag, the OS) fit in without translation. `docs/` is written in Chinese.
8. **Prefer maintained libraries; care about behavior, not details.** Use a maintained external library wherever one meets the need, and build our own only when none is maintained or none fits. Library code is cheaper to maintain and easier to review than our own. Each library choice is a design decision, listed in `docs/design.md` §3 and logged in `docs/decisions.md`. Effort goes into the overall behavior that the properties state, not into hand-tuning details.
9. **Expensive verification runs only with the user's approval.** A lane runs `make check` once, with the default rapid settings, and commits. Mutation testing (gremlins), long fuzzing and high rapid counts are `make deep`. Nobody starts it on their own: not a lane, not a review, not the main session, not a scheduled job. When a piece of development is done, the main session reports it to the user and proposes a deep run, and runs it only after the user agrees. Each surviving mutant or failure it finds becomes a fix task for a later lane.
10. **The viewer shows data, quietly and formally.** A page shows data only: every explanation (a section's note, a legend, how to read a view, how a number is counted) sits behind a small ⓘ that shows it on hover, or another small interaction such as expanding in place. Node kinds, actions, statuses and links are icons from one maintained set (Lucide; `lucide-react` in the frontend), never word labels or typed ASCII/Unicode symbols. The page's wording is formal Chinese, taken from the term table in `docs/design.md` §7.5; nothing colloquial. The Figma prototype is the viewer's visual specification, drawn with the aegis kit's tokens and controls: a UI change is drawn there first, then built, and where the prototype and the kit disagree, the kit decides and the prototype is corrected.
11. **Every operation is a black box, and no hand-written predicate is kept.** A property relates an operation's inputs to its outputs (docs/model.md §3.4): a pure operation's result or raised error; for an operation with effects, also the state observed before and after the call (`observe`, bounded by `changes`). Effects are state among the inputs and outputs, not a special case. So a claim about effects (files, HTTP, processes, time) is a black-box property on the real operation: a derived input builds the state it starts from (docs/language.md §4.6), and a named observation reads the state back. Extracting a pure core is an optional engineering choice, made only where the shell's logic is too complex for expressions over observed state. A `manual` property or flow is a design defect to remove, not a place to rest: when a claim cannot be written as expressions, the property is split again and its claims reconsidered, and only what still needs a missing construct stays `manual`, with that construct named. A generator draws from its randomness: a symbol computed from earlier symbols is a derived input, bound to a function that returns its value, never a generator that draws nothing.
12. **The viewer is compiled, typed and accepted on this repository.** `unicode serve` answers only from the snapshot `unicode build` writes, evidence and reviews included; it builds its state once when it loads a snapshot and again only when the snapshot changes, never per request, and its answers carry `within` budgets. The TypeSpec interface in `api/` is the one contract: a field that only some kinds fill is modelled per kind, so a page cannot read what the server does not give, and any mock conforms to the same contract. A viewer change is accepted on this repository's own snapshot served by `unicode serve`, never on mock data: every view has content and every target on it can be reached, in light and dark, at desktop width and at 768 px.

## Roles and workflow

- The main session designs and reviews. It writes the design files, then dispatches implementation to subagents, one lane per coherent piece of work. Each task names the design nodes it implements and the documents to read (from M3 it carries `unicode slice`).
- A lane works in its own worktree at `../unicode-wt/<lane>` on branch `<lane>`, commits there, and never touches the main checkout.
- The main session reviews every lane with a code-reviewer subagent and by reading the code, rebases the lane's branch onto main, runs `make check` on the result, fast-forwards main to it (`git merge --ff-only`), and removes the worktree. History stays linear: no merge commits, `git pull --rebase` (or `--ff-only`) when taking the remote, and a lane that falls behind rebases rather than merges main in. Findings about the specification go into the documents as commits of their own on top. A review reads the code and may run a few targeted probes; it does not run batches of mutants, which belong to the deep stage.
- Lane briefs ask for `make check` and a commit, never for mutant confirmation or long runs.
- Main is green at every commit: nothing is merged into main or pushed unless `make check` passes on it. Work in progress stays on its branch, including design files that use a construct the parser does not accept yet and properties whose code is not written.
- Decision entries are numbered when they land: a lane rebasing for landing numbers its entries after main's last one, so two sessions never take the same number.
- A failure on main has one owner at a time; whoever takes it says so before fixing it, so that two sessions do not fix the same failure two ways.
- Probes of the viewer run in a private headless browser per lane, never in a browser shared with other agents, whose navigation leaks into the results.
- A review compares every changed summary or domain description with its predicate (the hand-written one, or the `ensure`, `requires`, `changes` and `call` it is generated from) or its generator, and every changed predicate or generator with its description.
- The toolchain itself never schedules agents.

## Go

- Go 1.26, module `github.com/lincyaw/unicode`. `make check` runs golangci-lint (with gofmt), `go test ./...`, `unicode fmt --check`, the full `unicode check`, and `scripts/rulecodes.py`, which keeps every numbered rule of docs/language.md and docs/model.md mapped to the diagnostic codes of the source (their appendix B) and rejects a string of the source that is written where a code is reported (a `Code` field, or the `code` parameter of a function that reports it) unless it is `<component>.<kebab-name>` of its own component, written where a code is compared (with `==`, `!=` or in a `switch` on a code) unless some component reports it, or that starts with its component's name and a dot and is not a whole code.
- Each package under `internal/` is one component. Its imports follow the design's `uses`, checked by golangci-lint's depguard until M2 and by `unicode check` from M2; a change to the depguard rules follows a change to the design.
- The libraries in use are listed in `docs/design.md` §3. Adding or replacing one is a design decision (principle 8).
- General Go rules belong in the conventions skill as `reference/go.md`. Until that reference exists, this section holds them.

## Python

- The Python backend's extraction script and the `uc` package use only the standard library. The skill's Python reference applies to them.

## Documents

- `docs/` holds documents only. Each subject has one current document, edited in place on each decision. Documents are in Chinese, direct and linear; clarifications go in an appendix.
- Summary strings in the design files (a declaration's summary, a `generated` domain description, a `manual` reason, and the `alt`, `opt`, `loop` and `else` labels) follow the rules of `docs/language.md` §4.2: one sentence that reads alone, terms only in their defined sense, and exactly what the code checks or draws.
