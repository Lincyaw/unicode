# unicode 工具链设计

unicode 把一个仓库的设计意图、代码和证据组织成一张图（[model.md](model.md)），设计意图写在设计文件中（[language.md](language.md)）。本文写工具链本身：用法、组件、语言后端、建图、生成与运行、视图与切片、命令行、计划，以及工具链对自己的验证。设计理由集中在附录 A，待定的事项列在附录 B。

## 1 目标

- **管理人的上下文**：人只看核心，也就是架构、流程、核心函数，以及每条性质和它的证据；细节在点开时才出现。
- **知识与代码一致**：结构从代码静态抽取，意图由设计声明，二者由检查对齐。没有对齐的知识会明确标出来。
- **设计先行**：先写设计，再按设计生成骨架、生成器和测试驱动，最后写函数体，以及人工性质的谓词。
- **性质和流程都可执行**：每条性质和每个流程都有一个谓词。测试驱动全部由工具生成，按覆盖录制下来的输入构成可以快速回放的回归集。
- **黑盒契约**：输入、前提、输出、观察值和允许变化的范围由设计声明；驱动调用真实的代码并核对，不展开函数内部算法。具名观察通过只读适配器接入。此路径不依赖定理证明器或 SMT 求解器。
- **结构统一，记法可换**：图只有一套结构（[model.md](model.md) §1），DDD、UML、时序图、事件风暴、C4 都是它的视图。

## 2 使用方式

工具链的使用者是设计者兼评审者，可以是人，也可以是 Claude Code 的主会话。写代码的工作由设计者派给 agent 完成。一轮工作分七步：

1. 设计者编写或修改设计文件：组件、类型、流程，以及带符号和用例的性质，直到 `unicode check --design-only` 通过。
2. 设计者运行 `unicode gen`，为缺少的设计节点生成骨架，并重写生成器、由陈述生成的谓词和驱动。
3. 设计者把要实现的设计节点派给 agent，任务附上这些节点的切片（`unicode slice`，§7.3）。
4. agent 写函数体和人工性质的谓词，自己运行 `unicode check` 和 `unicode test`（快路径），然后交回。
5. 设计者用 `unicode check`、`unicode test`、`unicode diff` 和视图评审交回的结果。通过就合入；不通过就带着诊断再派一次。
6. 慢路径 `unicode test --explore` 按时间预算另外运行，例如每晚一次。它把增加覆盖的输入和找到的反例录制下来，经评审后合入。
7. 部署之前，以正在运行的版本采集的真实调用回放并做版本差分，有不同就不部署（§8）。部署的程序带监控构建，在真实的调用上判定性质，结论经 OpenTelemetry 报告并写成运行记录，编进快照后与测试的证据并列显示（§6.6）。

工具链不调度 agent，也不保存任务。它只提供设计、生成、检查、运行和查询这几类能力。

## 4 语言后端

每种语言有一个后端，它实现接口 `Backend`，还可以实现接口 `Generator` 和 `Runner`（草案）：

```go
type Backend interface {
	Language() string
	Extract(root string, srcRoots []string) (Extracted, error)
	MapName(role NameRole, designName string) string
}

type Generator interface {
	Language() string
	Generate(plan GenPlan) Generation
}

type Runner interface {
	Language() string
	Run(plan RunPlan) RunReport
}
```

- **抽取**：后端读出 `container`、`type`、`op` 节点，以及 `contains`、`imports`、`calls`、`refers`、`extends`、`implements` 边。它同时读出代码中的绑定，写成 `realizes`、`checks`、`generates` 和 `observes` 边；绑定的写法不合格式时，给出诊断。带 `realizes` 绑定的类型，它的每个方法按反向的名称映射（例如 Go 的 `Submit` 对应 `submit`）得到一条到 `<类型的标识>.<操作名>` 的 `realizes` 边，来源为推导，称为**方法的候选边**；推导时，终点不存在的候选边被丢掉，那些方法是细节。代码层 `op` 的 `signature` 属性按下面的类型映射归一化成设计的写法，引用写成从根起的标识，与设计层的签名直接按字符串比较。后端产出的是代码层的图片段，格式与快照相同。
- **Go 后端**：在进程内用 `golang.org/x/tools/go/packages` 和 `go/types` 解析源码和类型。调用按静态类型解析，接口方法的调用解析到接口的方法。不在调用位置上的函数和方法引用（函数名、方法表达式 `T.M`、方法值 `x.M`）也算作调用，调用位置是引用的位置：引用得到的函数值可能被调用，这是可能的调用，与经由接口的分派一样取宽；对接口方法的引用指向接口的方法。调用和引用都属于能执行它们的函数：写在函数体中的，包括其中的函数字面量，属于这个函数；写在包级变量的初始值中的（例如函数字面量、按种类取函数的表，或 `var f = g`），属于引用了这个变量的每个函数，并经由初始值中引用的其他包级变量传递，位置仍是它在初始值中的位置。初始值中函数字面量之外的调用在包初始化时就执行，不属于任何函数，它调用的函数也不算被引用。`implements` 按 Go 方法集的类型身份判断，参数名和返回值名不参与比较；包的测试变体仍按同一包路径识别类型，有符号性、整数宽度与可变参数等真实类型差异保留。抽取包括 `_test.go` 文件：谓词、生成器和只供它们使用的类型都在其中，它们的绑定照常读取。
- **效果**：Go 后端为每个代码层操作记下直接效果（[model.md](model.md) §3.1），即它的函数体（包括其中的函数字面量）直接调用的、下表所列的标准库函数和方法所属的效果种类，加上它直接调用的依赖模块中的函数的效果；表外的标准库函数不算效果。依赖模块中函数的效果，按同样的规则在依赖模块的代码上沿调用求出，按模块的版本缓存，例如 `golang.org/x/tools/go/packages` 的 `Load` 经 `os/exec` 运行 `go list`，所以有 `process` 效果。`graph` 按 [model.md](model.md) §9 D8 沿调用求出每个操作的效果。Python 后端的对应表属于 M5。

  | 效果种类 | 直接调用的标准库函数和方法 |
  | --- | --- |
  | `time` | `time` 的 `Now`、`Since`、`Until`、`Sleep`、`After`、`AfterFunc`、`Tick`、`NewTimer`、`NewTicker` 和 `Timer`、`Ticker` 的方法；`math/rand`、`math/rand/v2`、`crypto/rand` 的全部函数和方法 |
  | `fs` | `os` 的函数和方法，下面 `process` 一行所列的，以及 `Expand`、`IsExist`、`IsNotExist`、`IsPathSeparator`、`IsPermission`、`IsTimeout`、`NewSyscallError`、`SameFile` 和 `LinkError`、`SyscallError` 的方法除外；`path/filepath` 的 `Abs`、`EvalSymlinks`、`Glob`、`Walk`、`WalkDir`；`io/ioutil` 的全部函数 |
  | `process` | `os/exec`、`os/signal` 的全部函数和方法；`os` 中读写进程及其环境的 `StartProcess`、`FindProcess`、`Exit`、`Executable`、`Hostname`、`Getpagesize`、`Getpid`、`Getppid`、`Getuid`、`Geteuid`、`Getgid`、`Getegid`、`Getgroups`、`Getenv`、`LookupEnv`、`Setenv`、`Unsetenv`、`Clearenv`、`Environ`、`ExpandEnv`、`TempDir`、`UserHomeDir`、`UserCacheDir`、`UserConfigDir` 和 `Process`、`ProcessState` 的方法；读写标准流的 `fmt.Print`、`fmt.Printf`、`fmt.Println`、`fmt.Scan`、`fmt.Scanf`、`fmt.Scanln`，以及 `log`、`log/slog` 的包级函数 |

- **Python 后端**：工具链内嵌一个只用标准库的抽取脚本，以 `python3 -I` 运行。脚本用 `ast` 解析源码，把图片段以 JSON 写到标准输出。调用按名称和导入关系解析，解析不到的调用不成边，只计数。生成在 Go 中按模板完成。
- **运行**：后端用该语言的测试工具运行生成的驱动。Go 按 §6.4 编译一次带 atomic 覆盖的二进制，每个输入独立执行并减去准备基线，读取真实基本块 profile；覆盖范围是谓词沿 `exercises` 可达的生产函数，不含生成文件和谓词本身。Python 的 `sys.monitoring` 接入属于 M5。
- **测试类别**：Go 中，`func FuzzX(f *testing.F)` 为 `fuzz`，调用了 `rapid.Check` 的 `TestX` 为 `property`，其余 `TestX` 为 `example`。Python 中，带 `hypothesis.given` 的测试为 `property`，用 `atheris` 的为 `fuzz`。后端据此找出生成文件之外的测试函数（[model.md](model.md) §10 第 21 条）。
- **名称映射**：

  | 设计 | Go | Python |
  | --- | --- | --- |
  | 类型 `Order` | `Order` | `Order` |
  | 操作 `unitPrice` | 方法或函数 `UnitPrice` | `unit_price` |
  | 字段 `unitPrice` | 字段 `UnitPrice` | 属性 `unit_price` |
  | 枚举值 `draft` | 常量 `OrderStatusDraft` | 成员 `DRAFT` |
  | 性质 `total-is-sum` 的谓词 | `checkTotalIsSum` | `check_total_is_sum` |
  | 流程 `submit-order` 的谓词 | `checkFlowSubmitOrder` | `check_flow_submit_order` |

- **谓词的签名**：参数依次是该性质或流程的符号，按名称映射，类型一致。Go 的谓词另有第一个参数作为测试句柄，类型为 `rapid.TB`；Python 的谓词没有测试句柄，用 `assert` 断言。
- **类型映射**：归一化签名用设计的类型写法，各语言的写法与它一一对应。例如：
  - `int` 对应 Go 的 `int` 和 Python 的 `int`；
  - `list<T>` 对应 `[]T` 和 `list[T]`；
  - `optional<T>` 对应 `*T` 和 `T | None`；`object` 类型在 Go 中按指针传递，`T` 和 `optional<T>` 都写作 `*T`；
  - `bytes` 对应 `[]byte`，`set<T>` 对应 `map[T]struct{}`，`map<K, V>` 对应 `map[K]V`，`float` 对应 `float64`，`time` 和 `duration` 对应 `time.Time` 和 `time.Duration`；
  - 实现设计类型的代码类型，写作该设计类型的标识；其余的代码类型写作它的代码标识，与设计的比较因此不相等；
  - `call<…>` 和 `replies<…>` 对应生成文件中按完整模型类型稳定命名的载体，以 `//uc:model-type` 注释保留精确类型。

  - `enum` 对应 Go 的 `type X string` 和常量 `X<值>`，常量的值是设计中枚举值的名称；对应 Python 的 `enum.Enum`，成员的值也是设计中的名称。
  - Go 函数或方法的第一个参数类型为 `context.Context` 时，它不进入归一化签名，设计中的操作不写它：它传递调用所在的轨迹，不是操作的输入。生成的驱动调用这样的函数时传入 `context.Background()`；运行时的包装用它连接轨迹（§6.6）。

  操作只有一个返回值；要返回几个结果时，写成一个记录。在 Go 中，`raises` 对应最后一个返回值 `error`，这是多返回值唯一的用法；在 Python 中，错误不出现在签名里。Python 中实现设计节点的函数和谓词，每个参数和返回值都必须有类型标注。
- **生成器的签名**：带 `generates` 绑定的函数，参数是在该符号之前声明的符号中它用到的那些（按声明的次序，可以没有），返回该符号类型的生成器：Go 为 `func genX() *rapid.Generator[T]`，Python 为返回 Hypothesis strategy 的函数。派生函数（[language.md](language.md) §6）的参数相同，直接返回该符号类型的值：Go 为 `func deriveX(…) T` 或 `func deriveX(…) (T, error)`，Python 为返回该值的函数。
- **观察适配器的签名**：参数是观察的 `from` 按次序列出的输入符号，类型一致，返回观察类型的值；Go 允许末尾另有 `error`，Python 的异常也按观察失败处理。它不接收测试句柄，不使用谓词的名称映射。一个适配器恰绑定一项观察，文件属于性质所在容器。
- **可选能力**：`lang.Backend` 只要求抽取与名称映射；后端还可以实现接口 `lang.Generator`，即**生成能力**，和接口 `lang.Runner`，即**运行能力**，两者都有 `language`。`generate` 接收生成输入 `GenPlan`，返回 `Generation`，称为**生成计划**：要写的文件和诊断，它不直接写仓库；`run` 接收运行输入 `RunPlan`，返回逐条性质和流程的结论 `RunReport`。各字段以 `design/lang.uc` 为准。`gen.plan` 为每种已配置的语言调用有生成能力的后端，合并成一份生成计划；`gen.write` 先检查全部路径、重复目标、符号链接和生成标记（§6.2），再逐个文件原子写入，多个文件之间不保证同时成功。`run.execute` 按目标标识调用各语言有运行能力的后端，并原子写出 `.unicode/results.json`。

### 5.2 节点的属性

图中每个节点的摘要字段是它的摘要，其余内容写在属性中。属性的值都是字符串的列表，类型和值都按规范格式写出。类型和节点引用写成绝对标识；表达式与变化路径保留源文本中引用的写法，并由 `refers` 保存已解析的引用：

| 种类 | 属性的键 |
| --- | --- |
| container | `focus`（取实际生效的关注度，子组件继承父组件的）、`labels`、`paths`（设计层）；`notations`、`roots`（只有 `system` 才有，`roots` 每项写作 `语言: 目录`）；`language`、`path`（代码层） |
| type | `labels`、`fields`（每项 `名称: 类型`）、`values`、`codec`（编码与解码操作的绝对标识）、`codecType`（成功校验后的有限表示类型） |
| op | `signature`（`(参数: 类型, …) -> 类型 raises 错误, …`）、`pure`（纯操作为 `true`，其余不写出） |
| flow、property | `symbols`（每项 `名称: 类型`，生成的符号另加 ` generated`）、`limits`（每项是一条限定的规范写法）、`call`（`call` 子句的规范写法）、`within`（时长）、`ensure`（每项一条表达式的规范写法，按书写次序）、`manual`（人工性质的原因） |
| property 的黑盒契约 | `requires`（按次序的前提表达式）、`observe`（直接观察路径、具名观察声明或 `none`）、`changes`（变化路径或 `none`）；`call` 只保存调用表达式，不带关键字 |
| observation（snapshot） | `type`（观察类型）、`inputs`（`from` 列出的输入符号，保持次序） |
| step | `index`、`label`、`args` |
| case | `values`（每项 `符号 = 值`）、`reason`（录制的用例） |

代码层的节点由语言后端写出，属性的键如下。凡是名称，都先按反向的名称映射换回设计的写法（例如 Go 的 `UnitPrice` 写作 `unitPrice`），`check` 因此不必知道名称映射，直接与设计比较：

| 种类 | 属性的键 |
| --- | --- |
| container（`package`、`file`） | `language`、`path`（文件的路径，或包的导入路径）；带生成标记的文件另带 `generated: true`；文件另带 `globals`（不是节点的顶层声明的 SHA-256，按源码次序） |
| type | `name`、`fields`（每项 `名称: 类型`；未导出的字段是细节，不列出）、`values`、`declaration`（类型参数和定义的规范形式 SHA-256，不含类型名或方法体） |
| op（`func`、`method`、`abstract`） | `name`（带 `checks` 绑定的谓词写作它检查的性质或流程的名称）、`signature`、`testKind`、`stub`、`body`（函数体规范形式的 SHA-256，无函数体时省略）、`declaration`（具体操作的原生声明头的 SHA-256，包含接收者、原生签名及泛型约束）、`directEffects`（直接效果，按 `time`、`fs`、`process`、`network` 的次序） |

`body` 和 `declaration` 让内容哈希含有实际的代码。Go 按语法树编码，依次记录节点类型与字段，位置只记有无，忽略注释；SHA-256 写成小写十六进制。声明头不含函数体，接口抽象操作没有原生声明头。

`calls` 边的属性 `sites` 列出每个调用位置，写作 `路径:行:列`；`generates` 边的属性 `symbols` 列出符号的名称。Go 签名的写法：指针 `*T` 写作 `optional<T>`，`check` 比较时把设计中 `object` 类型的 `optional<X>` 与 `X` 视为相同；末尾的 `error` 写作 ` raises error`，与设计中非空的 `raises` 相符；谓词的第一个参数（`rapid.TB`）保留在签名中，比较符号时跳过。绑定边的终点是设计层的标识。`Graph.AddFragment` 先暂存终点不在图中的绑定边和方法的候选边；推导时加入能解析的，绑定边中终点仍不存在的报为 `graph.unresolved-binding`，即 [model.md](model.md) §10 第 15 条中"目标存在"的一半；其余端点缺失的边仍是 `DanglingEdge`。

`alt` 中的步骤属于哪个分支，写在从 `alt` 到该步骤的 `contains` 边的属性 `branch` 上。空的列表不写出。

黑盒契约的 `refers` 边以 `clauses` 列出引用所在的子句，如 `requires#1`、`ensure#2`，以 `paths` 列出该引用访问的规范字段路径；同一对端点的引用合并，属性去重并排序。具名观察通过自身的 `refers` 引用观察类型。子句的具体源位置由 Go 后端生成代码时重新解析原文件、按性质标识和子句序号取得，写入生成的检查代码，不把行列号加入语义属性。

`extends`、`implements`、`uses`、订阅、调用、发起方和 `about` 都是边，不是属性。快照是 `{"nodes": [...], "edges": [...]}`：节点按标识排序，边按种类、起点、终点排序，属性的键按字典序排列。

### 5.3 需要代码才能判断的约束（M2）

`check` 在推导过的图上检查以下各项，诊断码写作 `check.<短横线名称>`，并给出每个声明项的状态：[model.md](model.md) §10 的第 12、14 至 20、22、34、39、40 条，以及第 24 条中"每个生成的符号恰有一个 `generates` 绑定"的一半。第 21 条对 Go 启用：实际声明文件没有生成标记（§6.2）时，测试入口报 `check.handwritten-test`；谓词和生成器不属于测试入口。Python 的驱动生成与本项检查在 M5 交付。第 28 条由 `unicode gen --check` 核对生成计划，并进入 `make check`；运行前仍核对将执行的生成文件。推导由 `graph` 完成，路径模式用 doublestar 匹配。

M2 的验收：`make check` 中加入 `unicode check`，在工具链自身上通过。

代码层 `op` 的 `attrs.body` 是去掉注释和出处的规范 Go AST 函数体；包括函数体中的闭包，接口抽象操作没有此属性。具体操作另以 `attrs.declaration` 保存不含函数体的原生声明头，包含接收者、原生参数与结果和泛型约束；从指针接收者改为值接收者也产生变化。代码层 `type` 的 `attrs.declaration` 是同形规范类型声明，不含方法体。以忽略注释和实际行列、保留位置有无的 AST 规范编码计算 SHA-256，排版和出处不进入值。比较只改函数体的工作区时也必须改变操作内容哈希；顶层变量的赋值跟踪仍按现有模型，不扩大为运行证据。

## 6 生成与运行

`unicode gen` 产生两类文件：骨架和生成文件。`unicode test` 运行生成的驱动。

M4 包括 Go 骨架、单次黑盒契约、调用序列、流程入口、接口与外部客户端替身，以及统一的回放、性质测试和原生 fuzz 驱动。覆盖挑选、缩减录制、流程内部轨迹核对和运行证据并图属于 M6；本节的快路径与预算内随机探索不依赖这些能力。生成或执行失败时给出诊断，不生成空的谓词，也不报告通过。

开发验证以 rapid 的配置次数为上限。普通 `go test` 先回放声明与录制用例，再执行按代价分配的次数（§6.3 的执行计划）；次数在开始执行之前定下，不按墙钟时间跳过剩余次数。只有 `unicode test --explore DURATION` 使用每条性质的时间预算；快路径 `unicode test` 只回放。`make check` 的 Go 包级超时为 20 分钟，容纳 CLI 性质反复载入临时模块的累计耗时，不增加探索次数或启动 `make deep`。

经单独授权的 `make deep` 不按代价分配，每条都执行 `RAPID_CHECKS` 次；它可配置 `RAPID_CHECKS`、`FUZZ_TIME` 与 `DEEP_TIMEOUT`；最后一项默认 `0`，避免高次数运行被普通包级超时截断。配置这项能力不启动深测。

每条可执行性质与流程另有一个原生入口 `FuzzUnicode_<完整ID的SHA-256小写十六进制>`，交给 `rapid.MakeFuzz` 从字节构造输入。名称只取决于完整设计标识，与声明次序无关，长度固定，Go 在 `testdata/fuzz` 下按入口名称存放的 corpus 因此始终属于同一条性质；入口注释写明设计标识。入口与普通测试共用按声明次序生成输入和调用谓词的逻辑；随机测试、探索和 fuzz 向手写的谓词传入真正的 `*rapid.T`，声明用例逐个以 `*testing.T` 回放一次。拒绝的候选输入由 fuzz 跳过，不算域外输入。fuzz 核对单个输入的关系与范围，`within` 的第 95 百分位由批次性质测试、回放或探索核对。每次执行结束或失败都恢复驱动的上下文，报告互不串用。生成声明与手写代码或另一项生成声明冲突时给出诊断。

旧驱动迁移逐条核对谓词、符号次序、自定义生成器及额外断言。原驱动使用的非通用分布以 `generated` 和 `generates` 明确绑定；专门的输入子域声明独立性质，保留各自的完整测试次数。迁移后删除手写 `TestX/FuzzX` 入口，手写的谓词和生成器仍保留。`gen` 只改写生成文件；本次手写入口由开发迁移删除，`gen` 不猜测、也不改写手写的断言。Go 的普通测试、fuzz 与新增性质入口此后统一随 `unicode gen` 更新，`check` 拒绝生成文件之外的 Go 测试入口。

`unicode gen --check` 按同一份生成计划逐字节核对全部目标，缺失或陈旧时报错，不创建目录、改写文件或跟随符号链接。它与 `--dry-run` 互斥，JSON 保留完整生成计划与诊断，成功的文本输出为空。`make check` 在运行 Go 测试之前检查格式、生成内容、自身绑定、规则码和 API 产物，避免在已知陈旧的代码上重复测试。

计算生成计划时，后端可以另用 `lang.GenerationExtractor` 抽取：Go 后端经 `go/packages` 的 `Overlay` 在内存中替换文件内容，把源码根目录中带生成标记的测试文件读成只有包声明的文件（保留生成标记、构建条件和 `//uc:model-type` 载体），再抽取手写代码和绑定。它只替换常规文件，不跟随符号链接，手写源码的错误照常报出，也不改动磁盘。Go 后端生成代码时自己加载代码，也用同一规则。普通的 `check`、`build` 和 `test` 仍按磁盘上的生成文件严格抽取；生成不能被旧生成文件中的类型错误阻止，否则接口改名之后无法重新生成。

Go 的旧生成测试若已不再承载任何性质，仍进入生成计划并改写为空包，保留生成标记和构建条件，清除陈旧谓词与入口。这样删除或移动性质后，旧驱动不会继续编译和运行；只读检查同样核对这些文件。手写文件与其他工具的生成文件不参与这项清理。

单次调用的黑盒契约按 [language.md](language.md) E12、E17–E23 执行。生成文件首行是生成标记（§6.2）；Go 的谓词与被测代码放在同一包的生成测试文件中，测试时用包路径和固定入口选择运行，输入在每次运行内重新构造。生成的代码按真实的 Go 签名构造调用与值，不从归一化签名猜测指针。执行结果包含有效执行数、拒绝的候选输入数、观察范围、范围外的差异和各子句的诊断；观察失败是检查错误，不算反例。没有有效执行时不能报告通过。表达式中的纯操作会重复调用并比较结果、接收者与实参；被测操作声明为纯时，也重复调用；冻结第一次的返回值或声明的错误，比较两次结果与错误数据，以及调用前后接收者和实参的模型值，包括无返回值的操作。第二次调用用于纯性检查，后置陈述读取第一次结果，计时也只计第一次。纯性诊断指向实际操作并保留子句位置；运行结论并入快照后的状态传播属于 M6。

### 6.1 骨架

骨架只在缺少时生成一次，之后归人或 agent 所有。`gen` 只新增，从不改写已有的代码元素。生成计划中 `Edit.createOnly` 为真的文件，即使目标带生成标记也不改写：先检查全部目标，再只在目标不存在时创建。骨架不带生成标记。重新建图再运行 `gen` 时，已有绑定的节点不再产生骨架；再次写入旧生成计划中 `createOnly` 的文件，因目标已存在而报冲突。新声明以稳定的逐节点文件写出，已有类型缺少的方法写进新文件，不改用户文件。空组件使用其路径模式中唯一确定的目录，已有包沿用包名，新包按目录和 module 确定；不能唯一确定时诊断，不猜路径。计算生成计划时，先在内存中加入骨架（不写磁盘）并解析它们的绑定，所以一份生成计划同时包含骨架和引用它们的驱动；目录尚不存在时也能算出生成计划，普通抽取仍然严格。`--dry-run` 和 `--check` 均不写骨架。它为以下各项生成骨架：

- 每个在代码中还没有的类型：带 `realizes` 绑定的类型，字段和操作按名称映射，方法体是占位标记。继承字段按已解析的声明类型定位实际 Go 嵌入路径，生成、字面量与读取共用该来源，不采用可能歧义的全局字段提升查找。继承操作的纯性同时核对实际声明类型的接收者视图，子类型遮蔽字段不能隐藏父状态的修改。具体基类已经提供的继承方法保留，不为它生成同名的骨架；接口要求的方法也先检查嵌入基类是否已经提供。占位标记在 Go 中是 `panic("unicode: unimplemented")`，在 Python 中是 `raise NotImplementedError("unicode: unimplemented")`，函数体恰好是这一句时就是骨架。
- 每个在代码中还没有的、容器或外部系统直接提供的操作：带 `realizes` 绑定的自由函数。外部系统的操作，生成在 `uses` 它的容器中，作为客户端。
- 每条没有谓词的人工性质或人工流程：带 `checks` 绑定的谓词，参数是它的符号。
- `replies` 输入需要但缺少的外部安装器：带 `substitutes` 绑定的自由函数骨架。先加载真实客户端与客户端骨架，再用其精确原生签名生成安装参数，返回 `func()` 清理函数；默认名称为 `install` 加外部系统和操作名称的大驼峰形式，再加 `Double`。函数体仍是占位标记，依赖安装器的目标保持 `stub`。
- 每个缺少自定义生成器的 `generated` 符号：带 `generates` 绑定的骨架，接受全部前置符号并返回该符号的 rapid 生成器；用户可实现后收窄未用的依赖。默认名称为 `gen` 加性质或流程名称的大驼峰形式，再加符号的首字母大写形式，流程在名称前加 `Flow`；同一包撞名时诊断，绝不改写已有函数。已有自定义生成器的名称由绑定确定，可服务多个符号，不强制改名。

### 6.2 生成文件

生成文件归 `gen` 所有，每次运行都按当前的设计整体重写，人不编辑。文件的第一行是**生成标记** `// Code generated by unicode. DO NOT EDIT.`。`unicode check` 确认它们与 `gen` 的输出逐字节相同（[model.md](model.md) §10 第 28 条）。生成文件包括：

- **生成器**：每个符号一个，按它的类型递归构造：
  - 内置类型取该语言的生成器，区间和大小作为取值的上下界；
  - `record`、`object` 和 `event` 由各字段的生成器组合而成；
  - `enum` 从枚举值或限定的子集中取；
  - `list`、`set`、`map` 按大小的限定生成；
  - `optional` 在 `none` 和 T 的值之间取；
  - 字段的类型为 `interface` 时，取该接口的替身；
  - `call<…>` 先选一个操作，再按它的参数类型和限定生成实参。

  生成的符号不按类型构造，用 `generates` 绑定的生成器；派生输入由派生函数算出（[language.md](language.md) E24）。Go 的驱动调用派生函数时，把临时目录（`TMPDIR`）指向这个用例自己的一个新目录，用例结束时删除这个目录，所以派生函数经 `os.MkdirTemp` 建出的状态随用例删除（E25）；派生函数返回错误或 panic 时报 `lang.golang.derivation-failed`，是检查错误。其余符号的取值域（[model.md](model.md) §3.3）只写在设计中一处，生成器和用例的检查都由它推出。
- **谓词**：每条带陈述的性质和每个流程一个，按 [language.md](language.md) §4.4 的检查步骤把 `call`、`within` 和 `ensure` 翻译成该语言的代码，带 `checks` 绑定；自动流程的谓词执行流程的第一个同步步骤。该步骤的实参必须是流程的输入符号且类型逐一匹配；类型方法须有唯一的该类型输入作为接收者。步骤树中的内部调用不由驱动重复执行，实际操作自行执行它们；内部顺序、事件和分支的运行核对属于 M6。需要文件系统、HTTP 等环境准备的流程是人工流程：写 `manual` 和理由，绑定手写的谓词；生成的驱动照常构造输入并调用它。`int` 用该语言的任意精度整数，例如 Go 的 `math/big`。人工性质没有生成的谓词。
- **调用的执行**：每个 `call<…>` 类型有一个执行器，把一个调用值作用到目标上，并返回该操作的结果或错误。有状态的谓词先检查初态，再逐步保存 `old`、调用和检查全部陈述；调用抛出声明的错误之后继续下一步，抛出未声明的错误则失败。Go 的调用值及应答脚本用生成的具名载体保存；生成文件中类型声明上的 `//uc:model-type 类型表达式` 只用于把载体映射回精确的 `call<…>` 或 `replies<…>`，不产生 `realizes` 边。这种注释只在生成文件中有效；计算生成计划时在内存中替换旧生成文件，仍保留这些不依赖执行的类型声明，以供手写的生成器引用。
- **替身**：代替接口的实现或外部客户端的测试代码，按输入中的应答脚本应答，也可以记下收到的调用和写入。接口字段以实现接口的具体类型填充，它带原生接口的全部方法；每个在设计中声明的操作，其应答脚本是输入值的一部分，在调用之前生成，被测调用执行时不抽随机数。接口值写成操作名到非空应答列表的记录。成功应答恰写 `{returns: 值}`，无返回值写 `none`；失败应答恰写 `{raises: "绝对错误标识", fields: {字段…}}`，错误须在该操作声明的错误或其后代中。每次调用取下一项，末项重复，输入有限而行为确定。

  替身要提供的原生接口方法都须在设计中声明；没有声明的方法不能以默认值假装应答。

  外部自由函数不能直接替换。它通过安装器（[model.md](model.md) §4）接入：参数恰为与真实客户端原生 Go 签名完全相同的函数，返回恰为 `func()` 清理函数；不修改客户端源码或机器码。自动的黑盒契约沿静态调用可达的每个外部操作须有唯一的安装器，以及一个 `replies<该操作>` 符号提供非空应答脚本。安装先于观察和前提；拒绝、失败和 panic 时都执行清理；安装失败或返回空的清理函数是检查错误（[language.md](language.md) E15）。普通调用仍使用真实客户端。
- **驱动**：每个谓词一个，以三种方式把输入交给谓词：
  - **回放**：把声明的用例和录制的用例转写成该语言的值，逐个交给谓词；
  - **探索**：由生成器产生输入，失败时把输入缩小到最小的反例；
  - **fuzz**：把 fuzz 引擎给出的字节，经生成器解码成各符号的取值。

  驱动每调用一次纯操作，就再调用一次，比较两次的结果、接收者和实参（[model.md](model.md) §10 第 32 条），第二次调用的 `set` 和 `map` 换一种元素次序（§6.5）；有 `within` 时，记下被测调用的耗时（[language.md](language.md) §4.4 E16）。
- **语言的对应**：

  | | Go | Python |
  | --- | --- | --- |
  | 生成器 | `rapid.Custom` | Hypothesis 的 strategy |
  | 探索 | `rapid.Check` | `@given` |
  | fuzz | `FuzzX` 中的 `rapid.MakeFuzz` | Hypothesis 的 `fuzz_one_input` 接到 atheris 上 |
  | 回放 | 普通的 `TestX`，逐个调用谓词 | 逐个调用谓词 |

  Go 后端在实现代码所在包生成 `unicode_contracts_gen_test.go`，一个包一个文件，普通入口是 `TestUnicodeContracts`，各性质按标识作为子测试；原生 fuzz 入口按完整标识稳定命名。生成的谓词带 `checks` 绑定，手写的谓词直接调用；人工流程的 `within` 计量整个手写谓词的耗时，要计量其中更小的部分时须拆分声明。所有方式共用输入与谓词，执行语义见本节开头；按覆盖挑选并录制用例属于 M6。

### 6.3 回放与探索

每个谓词的输入来自声明的用例（人写的）和录制的用例（探索挑选的）；带 `--traffic` 时另有采集的调用（§6.6），即部署的程序存下的真实调用。运行分快、慢两条路径。

- **快路径** `unicode test`：只回放声明的和录制的用例，结果是确定的。它是每次修改之后都跑的回归。加 `--since REV` 时，比较基准与工作区的设计层和代码层的节点及边，证据层、评审层和 `covers` 边的变化不会选中性质或流程；已有 `calls` 边仅 `sites` 行列位置变化不作为影响种子，新增、删除或其他属性变化仍保留。`imports` 边新增、删除或目标与非位置属性实变，以及代码文件的 `globals` 实变、含该属性的文件新增或删除时，从发起文件所属的代码包开始，沿 `imports` 反向逐级加入导入方代码包，把这些包的代码后代操作与类型作为种子，以包括初始化对同包其他文件及导入方的影响。再同时沿两张图的 §7.4 影响传播，选择当前仍存在的性质与流程；变化的用例归到它所属的性质或流程，删除的依赖仍从基准图传播。基准建图有诊断时阻断运行，不能据不完整图漏选。显式给出的未知标识先报错，合法标识与受影响集合取交集。没有受影响的性质和流程时成功结束，不运行任何谓词，保留上次真实运行的 results.json，不能把空集合当成全部运行；被选中的性质或流程没有有效执行仍报错。`--since` 另对设计未变、代码变了的操作做版本差分（§6.5）。
- **慢路径** `unicode test --explore DURATION`：在给定的时间内，按性质和流程分配预算，由生成器产生新的输入：
  1. 开始时，先丢弃已经不符合当前设计（[model.md](model.md) §10 第 26 条）的录制用例，再回放其余的用例，得到已有覆盖的并集 U。
  2. 每产生一个输入，就运行谓词并记录它的覆盖 C。C 中有 U 没有的部分时，这个输入以 `coverage` 为原因保留，U 并入 C。
  3. 谓词失败时，在剩余预算内把这个输入缩小，只接受仍然失败、并且失败不是检查错误的更小候选，以 `counterexample` 为原因保留，结束这条性质或这个流程的探索。最小指不能再缩小，不承诺全局最小。写入前须用冻结模型值再次复现。
  4. 探索结束后做缩减：声明用例和全部反例保留；按新增覆盖最多、同分时按规范输入的哈希的次序做确定性的贪心选择，再删除冗余的覆盖用例。保证覆盖的并集不变，不声称全局最小。每条性质或流程至多 64 个录制用例；若上限与保留反例、覆盖并集冲突，则明确报错，不改写旧录制文件。
  5. 加 `--record` 时，把结果写回 `corpus/` 下的录制文件，规范格式，按用例名排序。
- **覆盖**分两种，都写成 `covers` 边：
  - **代码覆盖**：谓词沿 `exercises` 可达的函数中实际执行的 Go 基本块，显示时投影到源码范围；
  - **设计覆盖**：流程中走到的步骤和分支，以及被调用操作声明的错误中实际抛出过的那些。
- **测试好不好**，用覆盖来衡量：一组用例的代码覆盖率、流程分支的覆盖率和错误的覆盖率，都显示在性质视图中。没有带来新覆盖的输入不录制，所以录制集保持小而有效。
- **流程的核对**：流程的驱动在执行时记录实现设计操作的函数被进入的次序和发布的事件，与流程的步骤树比较。次序不符时，谓词失败。
- 结果写到 `.unicode/results.json`，并以内容哈希为名不可变地保存在 `.unicode/runs/`。下一次建图时，每条性质和流程取它的当前证据（[model.md](model.md) §3.5）加入证据层；其余结论只保留为历史，不能标记当前通过、覆盖或纯性违规。

**执行计划。** 每次运行按下面的计划执行，快慢由它决定：

- **用例数按代价分配。** 生成的驱动对每条性质或流程 p 生成 n 个用例，声明的和录制的用例另外总要回放：n = min(N, max(1, ⌊T / d⌋))，N 是 rapid 的配置次数，T 是每条性质或流程的时间预算 10 秒，d 是 p 一个用例的估计耗时。p 的效果是它的谓词、生成器、派生函数和观察适配器的效果（[model.md](model.md) §9 D8）之并。有测量之前，d 由效果估计：没有效果或只有 `time` 时取 1 毫秒，有 `fs` 而没有 `process`、`network` 时取 20 毫秒，有 `process` 或 `network` 时取 1 秒；当前证据中有 p 的用例之后，d 取它们的平均耗时。纯操作上的性质因此执行满 N 次，到达进程或网络的性质少得多。`unicode build` 把每条的 n 写到快照旁的 `budget.json`，驱动启动时读取；没有这个文件时每条都用 N。
- **独立的性质并行运行。** `unicode test` 编译一次各包的测试二进制（§6.4），每条性质或流程在自己的进程中运行，进程之间不共享包级变量；同时运行的进程至多为处理器的个数。效果中有 `process` 或 `network` 的性质和流程可能共用端口、子进程和环境变量，它们彼此依次运行，与其余的并行。效果中有 `fs` 的只在派生输入建出的目录（[language.md](language.md) E25）中写入，算作独立。直接运行 `go test` 时，各包照 Go 的方式并行；包中生成的 `TestUnicodeContracts` 把每条性质或流程交给本测试二进制的子进程执行。一条性质的随机用例分给 8 与 rapid 配置次数中较小的那个数的子进程，各用不同的种子，用例数之和仍是配置次数；声明的用例只由其中第一个子进程回放；带 `within` 的性质只用一个子进程，第 95 百分位取自它的全部用例。同一台机器上同一个用户的全部测试二进制共用一个令牌池，同时运行的子进程至多为 `UNICODE_TEST_JOBS`，缺省为 GOMAXPROCS：令牌是临时目录下 `unicode-test-slots-<用户>` 中独占创建、写有持有者进程号的文件，持有者已不在运行的令牌被收回。一次运行的子进程共用为这次运行新建的内容缓存，运行结束时删除；设了 `UNICODE_CACHE` 时用它。每个子进程有自己的临时目录（`TMPDIR`）和进程组，结束后无论通过、失败还是被终止，父进程都终止它的进程组并删除临时目录。子进程的 `-test.timeout` 按它启动时剩余的时间给出，先于父进程的时限，超时时它自己打出各个 goroutine 的栈；父进程在 `go test` 的时限之前向仍在运行的进程组发送 SIGQUIT，十秒后终止。`-run` 和 `-skip` 的模式不含方括号、圆括号、`|` 或转义的 `/` 时，父进程按 `/` 分层读出哪些性质会运行，先一起启动它们的子进程；读不出时，等 `go test` 选中一条性质的子测试再启动它的子进程。全部子进程结束之后，父进程按性质的标识依次报告，每个失败的子进程报告写明性质、它是第几个子进程、它的用例数和种子，以及它的输出，其中有 rapid 给出的重放参数。子进程读取的文件和环境变量记回本进程的测试日志，`go test` 按它们缓存包的结果，与在本进程中执行时相同。统计覆盖、做性能剖析，或按种子或失败文件重放时（由命令行或 `RAPID_SEED`、`RAPID_FAILFILE` 等环境变量给出），性质仍在本进程中依次执行，失败文件写在包目录的 `testdata/rapid/` 下，与原来相同。
- **建出的状态做成模板。** 派生输入算出之后，派生函数在用例的目录中建出的状态（包括其中的 Git 仓库和 Go 模块）连同派生值保存为模板，放在 `UNICODE_CACHE` 给出的内容缓存的 `go-derived/` 中；`go test` 下这是为一次运行新建的缓存目录，所以模板在一次运行的各个子进程之间共用，运行结束时删除，没有设 `UNICODE_CACHE` 时不保存模板。键是性质的标识、派生输入的名称、运行中的测试二进制的 SHA-256（它含派生函数和从它可达的全部函数，比按 D8 求出的范围宽，依赖模块的改动也改变它），以及派生函数所用的前置符号的规范值。之后键相同的用例复制模板，不再调用派生函数：派生值中以原目录开头的文本换成用例自己的目录，文件用文件系统自己的复制逐个复制（Linux 上是 copy_file_range，在共享数据块的文件系统上即为克隆），保留目录、链接和权限位。每个用例得到自己的副本，结束时删除。状态中有文件或链接写着它的目录、派生值在文本中间写着它的目录、状态中有目录、普通文件和链接之外的东西，或派生值没有可回放表示时，状态不能移动，不保存模板，每次都调用派生函数。模板保存之后只被复制，不再写入。副本在新的目录中，而 Go 的构建缓存的键含有目录，所以在副本上运行的操作要重新编译它的包；这里不改用 `-trimpath`，因为那会改变依赖包导出数据中的位置，只为测试快一些不值得。
- **抽取和构建的结果按内容缓存。** 缓存是一个目录：环境变量 `UNICODE_CACHE` 给出它，缺省为用户缓存目录下的 `unicode/`，取值 `off` 时不用缓存；没有用户缓存目录而又没有设 `UNICODE_CACHE` 时报错。每一项以它的键的 SHA-256 为名，原子写入，几个进程可以同时读写；一项存在而读不出或内容不合格式时报错并写明这一项，不当作没有命中。Go 后端缓存三种结果，各在缓存目录下自己的子目录中：
  - 一次抽取（普通的或供生成用的）的节点、边和诊断；
  - 生成计划写入之后代码能否载入（§6.2）；
  - 覆盖插桩用的转发工具（§6.4）的可执行文件，键是它的源码和 Go 的版本与构建设置。

  前两种按键找到一项：键由运行中的 unicode 可执行文件的 SHA-256，`go env` 在仓库中给出的 Go 版本和构建设置，各源码根目录是目录、链接还是不存在，`go.mod`、`go.sum`、`go.work`、`go.work.sum` 和 `vendor/modules.txt` 的内容，仓库根目录、`go.mod` 的本地替换和 `go.work` 用到的目录之下 go/build 读入包的每个源码文件的路径和内容（跳过 `./...` 跳过的目录：名称以 `.` 或 `_` 开头的、`testdata` 和嵌套的模块），以及载入检查中计划写入的文件组成。路径相对于仓库根目录，同一份代码放在别处也命中；可执行文件的哈希使 unicode 的任何改动都让旧项失效。键之外，每一项还记下这次载入实际读取的输入：`go list -deps -test`（载入检查另加计划写入的文件的导入）列出的每个不在 GOROOT 和模块缓存中的包，它的目录中的名称，它读入的源码文件、忽略的文件和嵌入的文件的内容，它所在模块的 `go.mod` 和 `go.sum`，以及工作区文件。载入检查记下和核对这些输入时，把计划写入的文件当作已经写出，所以 `unicode gen` 写出驱动之后，`unicode test` 对同一份计划的检查仍然命中。命中时重新计算这些输入，有一个变了就不算命中，所以根目录之外的兄弟包、目录链接之后的包和嵌入的文件改动时，结果照样重新计算。只缓存成功的结果；载入之后再取一次键和这些输入，载入期间有改动时不写入。抽取和载入检查的项存为 gzip 压缩的 JSON。一项被读取时更新它的时间；每个缓存目录每天至多整理一次，删除连续 5 天没有被读取的项，再从最久未读的删起，直到这三个子目录合计不超过 512 MiB，只删除这三个子目录中的项。Python 的抽取结果按文件缓存，键是文件的内容哈希和后端的版本。带覆盖插桩的测试二进制按编译进它的全部源码（插桩之后的内容）的哈希、构建参数和 Go 的版本缓存；编译出的各个包由 Go 自己的构建缓存复用。
- **判定按键复用**（[model.md](model.md) §3.5）。`unicode test` 中，判定的键未变的用例沿用已保存的判定，不再执行，所以没有改动时不执行任何谓词，改动之后只执行执行输入哈希变了的性质和流程的用例。`--since REV` 在此之上只选 REV 以来受影响的性质和流程，并做版本差分（§6.5）。判定取自 `.unicode/runs/` 中的运行记录，按键建索引。
- **运行记录只留有价值的用例。** 运行记录中，每个用例都留下判定的键、判定和耗时；冻结的输入、覆盖和轨迹只留给反例和带来新覆盖的用例，覆盖的并集因此不变。录制文件同样只收反例和带来新覆盖的用例（上面的慢路径）。

### 6.4 Go 的覆盖、轨迹与录制

Go 先在不改动磁盘的前提下给源码插入 `runtime/trace.Log`，编译一次带 `atomic` 覆盖的测试二进制，再逐输入启动隔离执行进程。测试模式不能使用 `runtime/coverage` 的计数重置或写出接口：Go 1.26 的实际消费者已复现它们缺少测试元数据。每个候选写真实 `-test.coverprofile`，用已依赖的 `golang.org/x/tools/cover` 解析；不把百分比或累计计数当覆盖点集合。必要的模型解码准备以同输入的准备进程建立计数基线，执行进程减去基线，避免编码器、解码器的准备覆盖冒充谓词覆盖。元数据、非空 profile、源文件映射或候选报告缺失均为检查错误。

生成驱动增加内部候选协议，但普通测试和原生 fuzz 的既有入口、输入分布与默认次数保持不变。后端向候选进程提供 typed JSON 模型输入，或只请求依旧有生成器抽取输入；抽取进程与执行进程分开。候选接口以 `CandidateEvaluation` 区分真实结果、正常预算耗尽与检查错误；未完成的进程既不是拒绝输入，也不是反例。缩小从一个已经确认的反例开始，预算耗尽时保留它，缩小过程中的检查错误另列为诊断。

输入规范编码清空与 kind 无关的字段；标量的 items/entries 为 null，列表与集合的 items、记录/映射/调用的 entries 为空时为 []。float 用非指数的有限十进制文本，便于原样写入 corpus。模型值 wire 的 kind 为 none、bool、int、float、string、stringBytes、bytes、time、duration、enum、list、set、map、record、call、encoded、redacted；redacted 只出现在 `monitor` 写出的值中，text 是脱敏的摘要（§6.6），回放之前换成生成的值。标量放 text；string 是有效 UTF-8，非 UTF-8 的 Go 字符串以 stringBytes 的 Base64 原始字节保存，解码后为有效 UTF-8 时规范为 string；bytes 为 Base64，time 为 UTC RFC3339Nano，duration 为 Go 时长字符串，数值保留精确文本。list/set 用 items，encoded 的 items 恰一项；map/record/call 用 entries，记录字段和调用参数的键为字符串，call.text 是操作名。规范输入按符号名、记录和映射键、集合元素的规范编码排序，列表保序；inputHash 是规范化 Input.values 对象的 JSON 的 SHA-256，不包含外层 values 键。Input.values 不含派生输入（[language.md](language.md) E24）。

候选执行使用真正的 `*rapid.T`，其附加随机上下文从规范输入的哈希确定地派生；回放使用同一规则。输入在调用前冻结，替身取原始脚本，不能取调用后的状态。私有状态只能经类型的显式 codec 表示；不能保持规范表示往返的输入报错。有限值树没有引用身份；跨符号或字段的共享可变指针、映射和重叠切片若无法保持别名关系，拒绝录制，须合并到一个保持语义的 codec 输入，不能静默复制。codec 的缓存、nil 与空集合等原生细节是否相同由该类型的表示约定决定，不强制 reflect.DeepEqual。生成消费者只依赖标准库与 rapid，覆盖、轨迹解析和缩减策略留在工具后端。

轨迹解析使用 Go 项目维护的 `golang.org/x/exp/trace`，固定 `v0.0.0-20261124000051-d6646c509b6d`（要求 Go 1.26）；它提供真实 goroutine 标识与创建关系，不使用 `runtime.Stack` 文本猜 goroutine。插桩后的源码保持原路径与行号，不改仓库、go.mod 或 go.work；函数的进入和退出、声明的错误的抛出，以及发布函数的完成，是实际的事件。发布在发布函数进入时记起点，正常返回后才确认；panic 或没有返回的发布函数不算发布，异步订阅可以在发布返回前执行。只有主被测调用及其因果后代参与流程核对，观察适配器、前提、后置表达式和为纯性重复的第二次调用都不算作流程的步骤。异步关系按 goroutine 创建与发送、发布的先后匹配，不以全局函数栈模拟并发。

流程的 `alt/opt/loop` 标签是文本，不猜分支条件；步骤树定义允许的分支、可选及重复轨迹。多种合法解释无法区分时只记录所有解释共有的覆盖点，不猜某个分支；alt 以原标签计数，opt、on、loop 以 taken/skipped 计数，loop 的零次与至少一次分开。抛出声明的错误时走相应的 `on`，异步步骤须有先前的发送或发布。自动流程缺少真实入口、发布函数、轨迹数据或有不符合结构的调用时失败。人工流程仍由手写的谓词做环境准备和跨进程的调用；没有取得子进程轨迹时不填写设计覆盖或声称已核对内部步骤。

后端报告的 `RunResult.cases` 保存逐输入的冻结值、输入哈希、覆盖点、轨迹、耗时（[model.md](model.md) §3.5）及最终结果；拒绝的候选输入不成为反例，检查错误列在 `RunReport` 的 `diagnostics` 中。报告带版本 1、执行输入哈希、时间、提交、工作区状态和模式。`codeTotal/branchTotal/errorTotal` 是实际测量范围的分母；代码分母计基本块，不是行数或语句数。没有测量时相应指标缺省，不用零分母假装完全覆盖。证据层用 `contains` 连接 run/result，用 `about` 连接性质、流程和用例，用 `covers` 连接当前有效的 case 与代码、步骤；当前的反例和纯性违规参与一致性状态。

`--record` 仅与正的 `--explore` 一起使用。探索使用 `design.loadForExploration` 和后端生成抽取路径：先剔除不再满足符号、类型或限定的录制用例，并报告已无目标的录制文件；声明用例、语法、错误路径和其余设计错误仍阻断。自动的性质和流程的 `checks` 边在供生成用的抽取中被临时去掉时，按它的 `about` 和被测调用的实现代码所在的文件，或所属组件的代码文件确定配置的语言；人工性质和流程仍按手写谓词的 `checks` 绑定确定，不因缺少临时的生成边而丢掉目标。慢路径在内存中替换旧生成文件后生成当前驱动，不被旧生成测试阻断；缺少的手写谓词骨架不能被临时实现冒充。CLI 把实际执行的全部逐输入结果交给 `evidence.recordings` 给出录制文件，`evidence.applyRecordings` 检查后写入，随后 CLI 重新建图并生成当前驱动。给出全部规范的录制文件和已无目标文件的移除项，严格预检 corpus 路径、当前规范头和文件类型后写入；没有目标的文件只在 --record 时移除。随后用加入新用例的图重新计算生成计划并更新生成文件中的驱动，使下一次快路径可直接回放。生成与录制的每个文件分别按现有安全写入规则发布，不承诺跨文件事务；中途失败给出诊断并要求重试生成，不把陈旧输出报告为成功。没有 `--record` 时不改 corpus 或生成文件，但仍保存实际运行结果。名称前八位哈希冲突、无法复现的失败、覆盖上限冲突、编码失败、符号链接或无权改写都禁止伪成功。

### 6.5 推出的关系

[model.md](model.md) §3.3 的推出的关系不写成性质，由生成的驱动和 `unicode test` 检查；后三项不用于有 `time` 效果的操作（[model.md](model.md) §10 第 41 至 43 条）：

- **纯操作的确定性**（[model.md](model.md) 第 32 条）：驱动每调用一次纯操作，就再调用一次（§6.2）。
- **codec 的往返**（[language.md](language.md) §5.3.1）：录制和回放的输入，编码后解码再编码，规范表示不变。
- **元素次序**（[model.md](model.md) 第 41 条）：输入中有 `set` 或 `map` 时，驱动把其中每个 `set` 和 `map`，包括嵌在记录、列表和其他集合中的，按另一种元素次序重新构造，再调用一次。纯操作的这一次调用就是确定性的第二次调用；被测调用则从冻结的模型输入重新构造全部输入，派生输入也重新算出，再依次检查前提、取得观察值和调用。另一种次序由规范输入的哈希确定地选出，回放时不变。Go 的 `map` 没有插入次序，重新构造得到一份相等的值；Go 运行时每次遍历 `map` 都换一个起点，所以依赖遍历次序的代码在两次调用中通常给出不同的输出。
- **版本差分**（[model.md](model.md) 第 42 条）：`unicode test --since REV` 对设计未变、代码变了的每个操作 o 做版本差分。输入是以 o 为 `about` 的性质和流程在这次运行中的全部用例：声明的、录制的和生成的。没有这样的性质和流程、并且 o 没有效果时，输入按 o 的接收者类型和 `call<o>` 的生成器（§6.2）产生，每个输入只调用 o 一次。带 `--traffic` 时，o 的每个采集的调用（§6.6）也是一个输入，以它的接收者和调用值只调用 o 一次，按（o、采集的调用的输入哈希）对齐；部署之前的检查就是这样以真实的调用比较正在运行的版本和要部署的版本（§8）。基准一侧像查询的 `--rev` 一样取出 REV 的文件，在内存中生成驱动，只执行这些冻结的输入；两边各记下 o 的每次调用的输出，按（性质或流程、用例的输入哈希、o 在该用例中被调用的序号）对齐比较。基准的输出按（REV 的提交、o、对齐的键）缓存在 `.unicode/` 中，同一基准不重复执行。
- **实现差分**（[model.md](model.md) 第 43 条）：o 在两种语言中各有实现时，以 o 为 `about` 的性质和流程的每个用例，冻结的模型输入交给两种语言的驱动各执行一次，按版本差分的方式对齐比较。

比较两次执行的输出之前，输出中出现的派生输入建出的目录（[language.md](language.md) E25）的路径换成该派生输入的名称，因为每次执行建出的目录路径不同。元素次序的差异使所属性质或流程的结论不通过；版本差分和实现差分的差异列在运行报告外层的 `diagnostics` 中，指出 o、对齐的键和两边的输出。

### 6.6 运行时判定

部署的程序在处理真实的调用时判定性质（[model.md](model.md) §3.4，[language.md](language.md) §4.7）。`unicode gen` 为此写出监控文件；运行时包 `monitor` 提供组合根的接入、采样、轨迹和流程的核对、结论的报告，以及真实调用的采集。

**受监控的调用。** 一次调用经过下面两种包装之一，才是受监控的调用：

- **接口包装**：设计中的接口 I 由 Go 接口实现，并且有在运行时判定的性质或流程用到 I 的操作时，`gen` 为 I 写一个接口包装。用到是指：单次调用契约的被测调用的操作，或者不变式的序列符号中的操作，是某个实现 I 的设计类型中与 I 的一个操作同名的操作；或者流程的步骤调用 I 的操作。接口包装实现同一个 Go 接口，持有真实的实现；它的每个方法调用真实的实现，判定这次调用，原样返回结果。判定哪些性质由真实实现的 Go 类型决定：它实现的设计类型 C 中被调用的那个操作的性质，按 [language.md](language.md) E26 和 E27 判定，接收者是这个真实的实现；判定函数在实现所在的包中，见下文的监控文件。
- **入口包装**：容器直接提供的操作由 Go 自由函数实现，并且有在运行时判定的性质或流程用到它时，`gen` 为这个函数写一个同类型的包装函数，同样调用真实的函数、判定、原样返回。它用于程序的入口：注册给 `net/http` 的处理函数，以及命令行的命令所执行的函数。

组合根，即 `cmd/unicode` 的 `main` 或使用者自己的组合根，在构造时包装：接口的实现写作 `monitor.Wrap[I](实现)`，入口函数写作 `monitor.Entry(函数)`。监控文件在 `init` 中登记包装（见下文）；没有登记时，这两个函数原样返回参数。所以组合根在默认构建和监控构建中是同一份代码，监控是否打开只由构建条件决定。不经过这两种包装的调用不受监控：对具体类型直接调用的方法，以及不经入口包装、被直接调用的自由函数。

**监控文件。** Go 后端在两种包中写 `unicode_monitor_gen.go`，一个包一个文件：声明了带包装的 Go 接口的包，以及实现被判定的设计操作的 Go 类型或自由函数所在的包。它与 §6.2 的生成文件一样归 `gen` 所有，每次按当前的设计整体重写，由 `unicode gen --check` 核对（[model.md](model.md) §10 第 28 条）。它的第一行是生成标记，空一行之后是构建条件 `//go:build unicode_monitor`：默认构建不含它，`go build -tags unicode_monitor` 才把它编进程序，监控也就打开。它不是测试文件，不引入 `testing` 和 `rapid`，只调用非测试文件中的代码，所以写在测试文件中的观察适配器在运行时不可用，读它的子句不判定。文件中有：

- 接口所在的包中，每个接口 I 的接口包装类型，名为 `monitored` 加 I 的名称，例如 `monitoredBuilder`，字段 `next` 是真实的实现；
- 自由函数所在的包中，每个入口函数 F 的包装函数，名为 `monitored` 加 F 的名称，例如 `monitoredMain`；
- 实现所在的包中，每条在运行时判定的性质或流程的判定函数，名为 `judge` 加性质名称的大驼峰形式，流程在名称前加 `Flow`：它由与谓词相同的翻译（§6.2）从陈述生成，在调用之前完成 [language.md](language.md) E26 的前一半，返回在调用之后完成后一半的函数，结论作为返回值给出，不经测试句柄报告；
- 实现所在的包中，Go 值与模型值之间的转换、规范编码（§6.4），以及流程的步骤树，供判定和核对使用；
- 登记的 `init`：接口包装按接口的类型登记，入口包装按函数本身登记，判定函数按实现它的操作的 Go 类型或函数登记。

接口包装在 `monitor.Wrap` 包装一个实现时，按这个实现的 Go 类型取出登记的判定函数，所以接口所在的包不导入实现所在的包，监控文件不会在两者之间造成导入环。

监控文件中的元素都是细节（[model.md](model.md) §9 D6）。

**轨迹与流程的核对。** 接口包装和入口包装为每次调用开始一个 OpenTelemetry span，名称是被调用的设计操作的标识。Go 函数或方法的第一个参数是 `context.Context` 时（§4），span 以其中的 span 为父，传给真实实现的是带新 span 的 context；没有这个参数时，span 没有父 span。流程的步骤次序取自这些 span：第一个步骤的调用的 span 是根，经由 context 连到它的 span 依次是其中的调用。流程的核对器写在 `monitor` 中，Go 后端核对测试中的运行轨迹（§6.4）时也调用它：两种来源先转成同一种调用事件，即进入、返回或抛出的错误、事件的发布，以及因果上的父调用，再与步骤树比较。一个流程在运行时核对次序，要求它的每个步骤都能在轨迹中观察到：

- 步骤只有 `call`、`emit` 和 `alt`、`opt`、`loop`、`on` 片段，没有 `send` 和 `async`，因为后两者可能在第一个步骤返回之后、在别的进程中发生；
- 第一个步骤调用入口的操作或有包装的接口的操作，其余每个 `call` 步骤调用有包装的接口的操作，实现这些操作的 Go 方法和函数都以 `context.Context` 为第一个参数；
- 每个 `emit` 步骤发布的事件，它的每个发布函数都是有包装的接口的操作在实现类型中的方法，发布在这次调用正常返回时记下。

不满足时，这个流程在运行时只判定陈述，不核对次序。

**采样。** 每个操作有一个采样比例，在 0 到 1 之间。接口包装和入口包装对每次调用都开始 span 并记下调用事件，只对抽中的调用取值和判定，判定的开销因此按比例下降；流程在第一个步骤的调用被抽中时核对次序。比例由环境变量 `UNICODE_MONITOR_RATE` 给出，写作 `默认比例[,操作的标识=比例]...`，缺省为 `0.01`。

**判定深度。** 判定读取哪些值，由被调用的设计操作 o 的效果（[model.md](model.md) §9 D8）决定：

- o 没有效果或只有 `time` 时是**深判定**：读取 [language.md](language.md) E26 用到的全部值。
- o 的效果中有 `fs`、`process` 或 `network` 时是**浅判定**：调用之前读实参，调用之后读实参和返回值或抛出的错误；不读接收者，也不读直接观察路径。

具名观察在两种深度下都只在它的适配器廉价时读取，调用前后各一次。适配器**廉价**是指它的效果（D8）为空或只有 `time`：廉价与否由适配器的代码推出，不另写声明，所以读写文件、进程或网络的适配器不在真实的调用上运行。`gen` 按判定深度为每条性质在每个操作上定下判定哪些子句（[language.md](language.md) E26），写进判定函数。

读调用前后的状态，还要求这段时间中没有并发的受监控的调用改变它：同一个接收者上有另一次受监控的调用与这次重叠时，这次不读接收者；程序中有另一次受监控的调用与这次重叠时，这次不读具名观察，也不检查范围。读不到的值按 [language.md](language.md) E26 处理：读它的 `ensure` 不判定，读它的前提使这次调用不判定这条性质。结论记下每个子句被判定的次数，读者因此能看到哪些子句在运行时得到了检查。不经监控的并发改动看不到，设计也不描述并发（附录 B 第 6 条）。

**不改变真实的调用。** 判定只报告，不改变也不阻挡程序的调用：

- 真实的实现以原来的实参恰好调用一次，返回值和错误原样返回；判定不重复这次调用，也不调用其他操作，只调用观察适配器和表达式中的纯操作。
- 调用之前或之后的判定代码 panic 时，包装恢复它，记为检查错误，调用照常进行或照常返回。
- 真实的调用 panic 时，包装记下一次反例，再以同一个值继续 panic。
- 判定不在真实的调用期间持有锁；结论在后台写出，写不出时只计数（见下文的报告）。

**报告。** 判定的结论经 OpenTelemetry 报告，并写成运行记录：

- 每个反例、域外调用和检查错误是这次调用的 span 上的一个事件，名为 `unicode.counterexample`、`unicode.outside_domain` 和 `unicode.check_error`。事件的属性 `unicode.check` 是性质或流程的标识，`unicode.clause` 是不成立的子句、限定或前提，写作 `ensure#2`、`where#1`、`requires#1` 这样的序号，`unicode.input_hash` 是输入哈希；事件不带输入的值。
- 计数器按 `unicode.check` 计数：`unicode.monitor.applicable` 是适用的调用，`unicode.monitor.counterexamples`、`unicode.monitor.outside_domain` 和 `unicode.monitor.check_errors` 是三种结论，`unicode.monitor.write_failures` 是写不出的记录；直方图 `unicode.monitor.duration` 按 `unicode.op` 记下受监控的调用的耗时，以秒计。
- `monitor` 只依赖 OpenTelemetry 的 API（`go.opentelemetry.io/otel` 的 `trace` 和 `metric`），导出由组合根装上的 SDK 完成。`cmd/unicode` 在带同一构建条件的文件中装上 SDK 和 OTLP/HTTP 导出器，按 OpenTelemetry 标准的 `OTEL_*` 环境变量配置，所以默认构建不含 SDK。没有装 SDK 时，span 没有标识，流程不核对次序，其余照常。
- 每个**记录周期**（一分钟）结束时，`monitor` 为这个周期中有判定的性质和流程写出一份运行记录，格式与 `unicode test` 的相同（§8 运行的 JSON），执行场合为 `runtime`（[model.md](model.md) §3.5）。每条结论记下适用的调用数、域外调用数及各条不成立的限定或前提的次数、每个子句被判定的次数、检查错误、带 `within` 时耗时的第 95 百分位，以及反例：每个反例带冻结的输入、不成立的子句和时间，输入经过脱敏（见下文）；通过的调用不留输入。流程另记下核对的轨迹数。记录的提交和工作区是否有改动取自 Go 写进程序的构建信息，即 `runtime/debug.ReadBuildInfo` 的 `vcs.revision` 和 `vcs.modified`。记录写到环境变量 `UNICODE_MONITOR_DIR` 给出的目录（缺省为工作目录下的 `.unicode`）中的 `runs/`，文件名是内容的 SHA-256，所以几个副本同时写入互不覆盖。
- 部署的程序写出的 `runs/` 中的文件放进仓库的 `.unicode/runs/` 之后，`unicode build` 像对测试的运行记录一样把它们编进快照的证据层（§5），查看器因此只从快照读到运行时的证据（CLAUDE.md 原则 12）。运行时的结论的执行输入哈希，是记录的提交上该性质或流程的执行输入哈希：`build` 像查询的 `--rev` 一样取出这个提交并建图求出，每个提交只建一次，结果按提交缓存在 `.unicode/cache/` 中。记录的工作区有改动，或者没有提交时，结论没有执行输入哈希，只是历史。

**采集。** 环境变量 `UNICODE_MONITOR_TRAFFIC` 为 `on` 时，`monitor` 把抽中的调用的输入存下来，存下的调用称为**采集的调用**：

- 只采集深判定的操作的调用，即被调用的操作没有效果或只有 `time`：回放会在测试中再执行这些调用，读写文件、进程或网络的调用不能在测试中重放。接收者或实参含有类型为接口的字段时不采集：这种字段在测试中的值是应答脚本（§6.2），真实的实现没有对应的模型值。
- 一个采集的调用记下被调用的操作的标识（经接口包装的调用记下真实实现的设计类型 C 中的那个操作）、接收者的模型值（类型的操作才有）和调用值 `操作名(参数: 值, …)`，按 §6.4 的规范编码、经各类型的 codec（[language.md](language.md) §5.3.1）写出，另有程序构建所在的提交和时间；写出之前先脱敏。
- 采集的调用写到 `UNICODE_MONITOR_DIR` 中的 `traffic/<操作的标识>/<输入哈希>.json`，输入哈希按接收者和调用值计算，相同的输入只存一份；每个操作至多存 1000 个，存满后不再采集这个操作。
- 采集的调用不写进 `corpus/`：录制文件只由 `unicode test --record` 写入（[language.md](language.md) F3），是评审过的回归集；采集的调用来自真实的调用，数量随流量增长，并且可能含有用户的数据。

**脱敏。** 保存敏感数据的字段在设计中取一个带标签 `sensitive`（[model.md](model.md) §5）的具名类型。这种类型的值在 `monitor` 写出的每一处都被脱敏：采集的调用，以及运行记录中反例的输入。这样的值，无论是符号、字段、列表或集合的元素，还是映射的值，都换成规范编码中种类为 `redacted` 的值（§6.4），`text` 是原值的规范编码的 HMAC-SHA-256，写作小写十六进制。密钥取自环境变量 `UNICODE_MONITOR_KEY`，没有时由进程随机生成，密钥本身不写出。同一个密钥下相等的值脱敏后仍然相等，原值不能从中读回。OpenTelemetry 的事件和计数不带任何值，不需要脱敏。回放时，驱动把每个 `redacted` 的值换成按该类型构造的生成器（§6.2）以这个摘要为随机源取得的值，同一个摘要总得到同一个值。

**回放与部署之前的差分。** `unicode test --traffic` 把 `.unicode/traffic/` 中采集的调用回放为用例（[language.md](language.md) E29）：每条在运行时判定的单次调用契约和流程，以其被测调用（流程为第一个步骤）的操作的每个采集的调用为一个输入；每条在运行时判定的不变式，以对其类型 T 的对象的每个采集的调用为一个输入。带 `--since REV` 时，版本差分另以采集的调用为输入（§6.5）。部署一个新版本之前，以正在运行的版本的提交为 REV 运行它，差分有不同就不部署（§8 的部署）。

## 7 视图、切片与查询

### 7.1 视图

视图由三部分组成：从图中选取哪些节点和边、默认怎样折叠、元素按什么次序排列。视图只给出结构，不给出坐标，布局由前端完成。

**投影**只用结构，对任何项目都可用：

| 视图 | 输入 | 选取 |
| --- | --- | --- |
| 架构 `architecture` | 容器，缺省为整个系统 | 子容器、外部系统、`uses`、`depends` 及其状态；展开的容器另带其中的类型、操作、流程、性质和错误，类型带字段和枚举值与代码的逐项比较 |
| 类 `class` | 容器或类型 | 类型及其字段和操作、类型之间的边，以及被引用的其他容器中的类型（所在的容器折叠）；可以在设计层和实现它们的代码层类型之间切换 |
| 时序 `sequence` | 流程 | 步骤树、按首次出现排列的生命线、嵌套的激活、发送和发布，异步步骤所调用操作订阅的事件及其 `subscribes`，以及每一步的 `traces`、状态和设计覆盖 |
| 活动 `activity` | 流程 | 同一个步骤树，按控制结构画出 |
| 事件 `events` | 容器，缺省为整个系统 | 事件、发布它的步骤和订阅它的操作；错误、抛出它的调用步骤和处理它的 `on` 片段 |
| 调用 `calls` | 操作或函数 | 显著函数之间的 `calls` 和 `reaches` |
| 性质 `property` | 性质或容器 | 性质、`about`、符号、限定、用例（声明的和录制的）、谓词，以及覆盖率和最近的结果 |
| 代码 `code` | 文件或类型 | `contains`、进出的调用（一端在输入或它包含的节点中的 `calls` 和 `reaches`，另一端的函数也画出），以及覆盖到它的用例 |

**带标签的记法**只在系统文件声明了该记法时可用：

| 视图 | 输入 | 选取 |
| --- | --- | --- |
| DDD `ddd` | 容器，缺省为整个系统 | 带 `bounded-context` 的容器，其中带 DDD 标签的类型和事件，以及它们之间的 `refers`、`extends`、`implements` |
| C4 `c4` | 容器，缺省为整个系统 | 按 C4 的标签分两层：系统上下文（人、系统、外部系统）和容器（带 `container` 标签的容器）；边是依赖，标上经过它调用的操作 |

时序视图和调用视图合起来回答"这个流程怎样走、经过哪些核心函数"。

### 7.2 折叠与展开

视图默认只显示显著的节点（[model.md](model.md) §9）。架构、类、调用、代码、DDD 和 C4 视图还按容器的关注度折叠；时序、活动、事件和性质视图不折叠，流程的每个参与者、被调用的操作、发布的事件，以及性质约束的容器、类型、操作或流程，都画出来，因为它们是设计者写进流程或性质的。折叠的规则：

- `core` 的容器展开。
- `support` 的容器折叠成一个节点，只显示名称、摘要和进出它的依赖。
- `utility` 的容器不画出来，指向它的依赖也不画，视图只给出未画出的 `utility` 容器的个数（`hidden`）。
- 细节函数不显示。显著函数之间经过细节函数的调用，画成一条 `reaches` 边，标明经过了几个细节函数。

视图的输入 `expand` 列出要展开的标识：

- 展开一个折叠的或未画出的容器，显示它的内容；
- 展开一条 `reaches` 边，显示路径上经过的细节函数；
- 展开一个显著函数，显示它直接调用的细节函数。

视图的输入节点、包含它的容器和展开的标识都不折叠。展开一条 `reaches` 边时，标识写作 `reaches <起点> <终点>`。输入是细节节点或不存在的标识时，视图不适用；命令行先检查标识是否存在，不存在时退出码为 3。`view.inputs` 给出一种视图接受的全部输入，即以它为输入时视图适用的节点。

指向折叠的容器的边合并成一条，标明合并了几条；合并的边没有单独的预览。

展开的状态只存在于视图的输入里，工具链不保存它；前端把它写在页面地址中。

### 7.3 切片

切片是回答一个问题所需的最小上下文。人在详情中看到的，和派给 agent 的任务所附的，是同一种切片。一组节点 N 的切片包含：

- N 中每个节点的完整声明、状态和出处；
- 每个节点到 `system` 的祖先链，只给摘要；
- 每个节点沿各种边一步可达的显著节点，只给摘要；细节节点只给个数，展开之后才列出；
- 按种类补充的内容：
  - 操作：所属类型的字段和各操作的签名、订阅的事件、约束它的性质、调用它的流程步骤、实现它的函数的位置；
  - 性质：它的 `about` 所指节点的签名、各符号的类型及其字段、限定、前提、观察与允许变化的范围、具名观察的观察类型和适配器、用例，以及谓词的位置；
  - 具名观察：父性质、观察类型及其字段、输入符号的类型，以及适配器的位置；
  - 流程：符号、步骤树和每一步的 `traces`；
  - 容器：子容器、`uses`、带状态的 `depends`，以及类型的摘要。

按种类补充的内容放在切片的 `extras` 中，输入节点本身不重复列出，其他部分之间允许重复（例如操作所属的类型既是祖先，也在 `extras` 中）。性质的符号类型沿 `refers` 只经过类型逐层展开；具名观察另从父性质的 `symbols` 解析 `inputs` 对应的输入类型，展开其字段类型及观察类型，并包含 `observes` 的适配器；流程给出整棵步骤树和每一步 `traces` 的终点；容器要补充的内容都在一步之内，没有 `extras`。`get` 的边按种类、起点、终点排序。

切片的 `edges` 是两端都在切片列出的节点之中的 `contains` 边，由它还原祖先链和流程的步骤树。

代码只给位置（路径和行号）；加 `--with-code` 时附上源码，JSON 中为 `code`：标识到源码，源码是包含该节点的顶层声明及其文档注释所占的各行，由 Go 后端的 `declaration` 给出，查看器的源码片段也用它。目前只有 Go 后端提供，Python 到来时成为后端接口的一个操作。

### 7.4 影响与索引

- **影响**：对一组变更的节点 C，影响是沿 `calls`、`reaches`、`refers`、`subscribes`、`emits`、`realizes`、`traces`、`exercises`、`depends`、`about`、`checks`、`observes`、`substitutes` 反向能到达 C 的节点。结果按种类分组，每一项附上一条最短的路径，说明它为什么受影响。默认只列显著的节点。
- **绑定的影响**：代码的实际变化还沿 `realizes`、`checks`、`generates`、`observes` 和 `substitutes` 正向到绑定的设计节点，因此只改函数体、谓词或生成器也能选中相关检查。另从变更的适配器沿 `observes` 正向到观察，再沿该观察的 `contains` 反向到父性质；不沿其他 `contains` 传播。观察类型变化仍沿 `refers` 和 `observes` 反向影响适配器。说明路径保留图中边的原始方向，观察绑定可以逆向读出，因此路径是一串首尾相接的原图边，不要求每一条都按 `from` 到 `to` 遍历。
- **索引**：可以按标识、名称、种类和摘要文字查找节点，并按边反查，例如谁调用了它、谁订阅了这个事件、哪些性质约束它。

### 7.5 查看器

查看器只渲染图，不另存数据。视觉规范是 Figma 原型（文件 `inTTk3ypjVqoB9tHq0ErO4`），用 aegis-bench-site 套件的令牌和控件绘制；界面的改动先画进原型，再写成代码。原型与套件不一致时以套件为准，并更正原型。

查看器由工具链提供：`unicode serve` 启动一个小型后端，读取本地 `unicode build` 编译出的数据，提供查询与交互的接口，并提供前端页面。接口用 TypeSpec 定义，由各视图需要显示的内容推出（§7.5.1）；前端的源码在 `web/`，只通过这些接口取数据。前端的构建结果嵌入 `unicode` 程序，`unicode serve` 因此在任何仓库中都能提供页面（§8）。

- **视图是入口，实体页是落点。** 顶部的视图标签是探索的入口，每个标签都能进入：输入取自选中项，没有时取当前组件或整个系统中的缺省输入，由服务端给出（§7.5.1 的 `tabs`）；只有图中没有该视图能接受的输入时（例如系统文件没有声明该记法），标签才不可选，原因收在悬停提示中。类型、操作、流程、性质等节点各有实体页。图上的节点、设计树的条目、链接都能进入实体页，实体页中的引用又能继续进入下一页：页面上出现的每个节点名称都是链接，包括标题区路径中的祖先、顶栏的系统名、步骤的调用方和被调用方、签名和字段中的类型；列表和卡片折叠成的"+n"都在原处展开，展开后不再折回，离开该页或改选节点后恢复折叠。右栏在视图中预览选中的节点，在实体页中显示导航路径。视图、选中项和导航路径都记在地址里。
- **画布不窄于 480px。** 设计树、画布和右栏并排，设计树和右栏的宽度由读者拖动调整。窗口放不下设计树、480px 的画布和右栏（两栏按各自当前的宽度）时，右栏先收成抽屉；连设计树和 480px 的画布也放不下时，设计树也收成抽屉。收起的栏由标题行两端的按钮打开，从它那一侧滑出，盖在画布上，宽度是该栏当前的宽度，另一侧至少露出 48px 的画布；抽屉打开时取得焦点，画布不可操作，Esc 关闭抽屉并把焦点还给按钮。窗口变宽到放得下时，抽屉合上，该栏回到原处。
- **页面只放数据。** 说明性的文字，例如小节的说明、图例、读法和计数口径，收进标题旁的 ⓘ，悬停时显示；页面上不出现"点击……""另有……"之类的提示句。
- **能用图标的用图标。** 节点种类、操作、状态和链接用图标表示，不写成文字标签，也不用手打的符号。图标取自 Lucide（前端为 `lucide-react`），16px（小字旁 14px，标签内 12px），笔画 1.4，颜色随文字。状态用圆点：绿色为已验证，黄色为缺失，空心为骨架，红色为不一致。
- **操作标出效果和平均耗时。** 类型卡片、调用视图和代码视图中的操作和函数，以及操作页的标题，在名称旁用图标标出它的效果（[model.md](model.md) §9 D8）：没有效果，或者时间或随机数、文件系统、进程、网络中的每一种；效果不确定时不标。操作页另显示平均耗时（[model.md](model.md) §3.5），不确定时不显示。
- **运行时的证据与测试的证据并列。** 性质和流程的证据按执行场合（[model.md](model.md) §3.5）分开显示，各以场合的图标标出。运行时的证据显示记录的提交和周期、适用的调用数、域外调用数及各条不成立的限定或前提的次数、每个子句的判定次数、反例的输入和不成立的子句，带 `within` 时另有耗时的第 95 百分位，流程另有核对的轨迹数。只有在运行时判定的性质和流程（[model.md](model.md) §3.4）才有运行时的证据；用例和反例的历史中，每一项也以图标标出执行场合。
- **类型卡片显示内容。** 类型卡片列出设计中写出的字段、枚举值和操作签名，字段最多 6 个，其余折叠为"+n"，点"+n"在原处展开全部字段，画布让展开的卡片留在视野内；代码中多出的字段算细节，不列出。折叠的组件列出其中的类型名称，名称排成卡片高度所容的几行，放不下的截短并以省略号结尾，悬停时显示全名；操作签名同样截短。
- **单击预览，双击进入。** 单击节点在右栏预览；双击节点，或点右栏标题旁的 ↗，进入实体页。卡片里提到的其他节点（字段的类型、操作、折叠组件中的类型、外部系统的操作）各自是一个点击目标，同样单击预览、双击进入；点卡片的其余部分预览卡片本身。一个控件不嵌在另一个控件里。
- **画布保持可读，随手势移动。** 视图的画布按适合窗口的比例打开，但不小于 80%，放不下的部分由读者移动查看。按住 Ctrl 或 Cmd 转动滚轮、在触控板或触摸屏上双指捏合，以指针处为中心缩放，比例在 25% 到 200% 之间；直接转动滚轮、在触控板上双指滑动、用鼠标或单指拖动，都移动画布；拖动超过几个像素就不算点击，不会选中起点处的节点；从卡片里的引用、链接、ⓘ 和展开箭头上按下不拖动画布，留给它们自己的点击。画布上的拖动用于移动，因此不能拖选卡片中的文字，需要复制时到实体页中复制。右下角的缩小、放大和适合窗口与百分比始终一致。每个视图（输入、层和层级）的缩放和位置在本次会话中保留，回到该视图时恢复。画布本身不滚动：选中项不在视野内时（从设计树选中，或由地址给出），以及键盘把焦点移到视野外的节点或边时，画布把它移进视野并标出。
- **连线互不重叠，标记不压内容。** 同一行出入的多条线在行内错开，一条通道两侧的线出入方框的高度相间，经过两列之间时各走一条竖道，所以没有两条线重叠的一段，每条线都有一段只属于它、能点中的部分；线多的行随之加高。线上的标签和徽标放在不压住卡片、芯片、计数和其他标记的位置：先试线的中点，再沿线向两端试，标签在线旁，徽标在线上；标签压在别的线上时带文字光晕。代码视图中，线上的标记放在线的外侧一端所在的通道边上的一列，竖道让开这一列，一列中放不下而会相互重叠的标记分到并排的几列；折叠的组件画得与连到它的线所需的高度一样高，每条线都从它身上出发。
- **选中按套件的写法标出。** 选中的行（设计树的条目、步骤的标签、表中的行）用 `--row-chosen`：左侧一道渐变竖线和浅灰底；选中的卡片、组件、节点芯片和其他方框用静止的 ∞ 流光边（控件用 `loop-edge`，本身不是控件的方框用 `loop-edge-still`），卡片另加浅灰底；选中的边加粗。品牌色 `--accent-brand` 只用于焦点环。

#### 7.5.1 接口

**数据来源。** 查看器显示的图、证据和评审只来自 `unicode build` 写出的快照 `.unicode/graph.json`，快照中已经编入证据层和评审层，服务端不读运行和评审存储；代码的摘录另从工作区读源文件，工作区的提交取自 build 记录和 git（见下文），比较的基准由命令行建图。载入快照时，服务端按 `unicode check` 的约束检查一遍，得到诊断和每个声明项的状态，用 `review.recorded` 从评审层还原出评审记录，并算出每个页面都要读的结果：每种视图的输入、按目标索引的评审结果，以及每个设计类型的成员与代码的比较；这些结果每个快照只算一次，与每个基准提交的比较和对它的评审计算也在一个快照上各只算一次。快照文件改变后（按修改时间和大小判断），下一次请求时重新载入；每个请求只从一个快照回答。`unicode test` 和 `unicode review record` 只写各自的存储，新的运行结果和评审记录由下一次 `unicode build` 编进快照之后，查看器才显示（`cli.stores-reach-viewer-through-build`）；存储的读取诊断由 `build` 报出。应答的时限由 `design/serve.uc` 中带 `within` 的两条性质给出。快照所在的工作区取自 `build` 写在快照旁边的 `build.json`：其中的提交和是否有改动，另由 git 给出该提交的缩写、说明、时间和检出在它上面的分支，git 读不出时这几项为空；记录的提交为 `null` 时只有是否有改动。没有 `build.json` 时，在读入快照时由 git 给出；`build.json` 不是 `{commit, dirty}` 时，快照算作读不出。比较的基准由命令行按查询的 `--rev` 的方式取出该提交并建图（`serve` 的 `Builder`），每个提交只建一次，在进程内保留；比较由 `graph.compare` 给出，`base` 和 `head` 的写法与 `unicode diff --format json` 相同，`head` 是快照所在的工作区。实体页的变更取自同一个比较：节点本身，以及在基准或快照中实现它的代码元素，各一项，没有变化的为 `unchanged`；代码类型和函数另有 `linesChanged`，即它的声明在基准提交中和在工作区中所占的各行之间，按 `git diff` 计的增加和删除的行数，一边没有时按空计。`/compare` 的各项不带 `linesChanged`。

**约定。** 接口只读：视图、输入、展开、选中项和导航路径都记在页面地址中，服务端不保存状态。标识中含有 `.`、`#`、`:` 和 `/`，一律放在查询参数里，不放在路径中。接口的源文件是 `api/*.tsp`，`api/openapi.yaml` 由它生成，`make api-check` 确认二者一致；各字段的含义和取法以源文件中的说明为准。证据（运行、结果、覆盖，M6；运行时的证据，M8）和评审记录（M7）的字段是可选的，图中有了这些数据之后才给出。

**形状。** 已有的形状都沿用，字段名与命令行的 JSON 相同：

- 节点和边是快照中的节点和边（§5.2、[model.md](model.md) §8），节点带内容哈希 `digest`。节点另有 `title`（页面上的名称）、`status`（`check` 给出的状态）、`refers`（它的 refers 边指向的节点，按标识排序：字段、参数、返回值、错误、符号和黑盒契约子句引用的类型与操作，代码层的操作另有函数体中用到的类型）、代码元素的 `bindings`（绑定边及其指向的设计节点）、步骤的 `step`（所在流程、序号、发起方、目标、接收方、外层步骤和子步骤）、操作的 `effects`（效果，按 `time`、`fs`、`process`、`network` 的次序，没有效果时为空；设计层操作取实现它的代码层操作的效果，不确定时不给出）和设计层操作的 `meanDuration`（平均耗时，以纳秒计，由 `serve` 载入快照时从证据层算出，不确定时不给出）；边另有 `status`。页面在字段的类型、签名和符号中，只把 `refers`（成员则为它的 `refers`）列出的标识画成链接，其余文字原样显示，不从文字中猜引用。
- 诊断与 `unicode check --format json` 的相同。一条边加另一端的节点沿用 `query.Neighbor`，切片沿用 `query.Context`，影响沿用 `query.Affected`，单个节点沿用 `query.NodeView`。
- 视图标签的去处由服务端给出：实体页和视图各有 `tabs`，每种视图一项，按标签的次序，给出从这个节点（视图则为它的输入）打开该视图的请求，或者打不开的原因。原因是闭集合：`undeclared-notation`（系统文件没有声明该视图的记法）和 `no-input`（图中没有该视图接受的输入），它们在页面上的字词在前端的术语表中。请求先取节点的相关视图中该种类的第一个；没有时取缺省输入，依次在节点本身、它的各级祖先和整个系统这几个范围中，按设计树的次序找第一个该视图接受的节点：时序和活动视图取流程，调用视图取显著的操作，性质视图取含有性质的组件，类视图取组件；代码视图取节点的代码所在的文件（代码元素所在的文件、设计节点第一个实现所在的文件、代码包或组件的文件中排在最前的一个），没有时取最近的、拥有文件的祖先组件的文件中排在最前、视图接受的一个，再没有时取设计树中第一个拥有文件的组件的这样一个文件；文件按三项排序：不是测试文件的在前（测试文件是语言标为测试文件的文件，Go 中即以 `_test.go` 结尾、只有 go test 才编译的文件；或者含有测试函数、含有带 `checks`、`generates`、`observes`、`substitutes` 绑定的代码的文件），其中落实设计节点的代码元素多的在前，再按路径；架构、事件、DDD 和 C4 视图取整个系统；这样都找不到时，取该视图接受的第一个输入（`view.inputs`，按标识）。所以 `no-input` 只在该视图不接受图中任何节点时出现。每个请求都经过与 `/views/{kind}` 相同的适用判断。
- 视图沿用 `view.View`（`kind`、`input`、`ancestors`、`expand`、`layer`、`level`、`nodes`、`edges`、`folded`、`hidden`），加上视图中各项的诊断。类型卡片带 `members`，即字段和枚举值与代码的逐项比较；容器卡片带 `contents`，展开时是其中的类型、操作、流程、性质和错误，折叠时是其中类型的名称；代码文件和代码类型带 `details`，即未画出的细节函数的个数；代码层的类型和函数带 `file`，即写着它的代码文件的标识，也就是路径与它的出处相同的文件；方法可以写在它的类型之外的文件中，所以不沿 contains 边去找。`members`、`contents`、`details` 和 `file` 都只有部分种类的节点才有，`ViewNode` 按种类拆成各自的形状，是下一步"接口精确化"的工作。边的一端是折叠的容器时，`count` 是它代表的边数；`labels` 是边承载的操作，每一项是操作的标识 `op` 和标签上的写法 `text`（设计中的名称，人发起的调用另带步骤的实参，例如 `submit(cart)`），按写法、再按标识排序；不同组件中同名的操作因此仍能分开，页面把每一项画成指向该操作的链接。
- 拒绝的请求返回 `{code, message, fix}`：标识、边、文件或接口不存在为 404 `serve.not-found`；视图不适用于输入为 400 `serve.not-applicable`，提交读不出为 400 `serve.bad-revision`，路径不是设计文件、录制文件或快照中的代码文件为 400 `serve.bad-path`，参数缺失或不合类型（包括不存在的视图、节点或边的种类），以及 `layer` 给了类视图之外的视图、`level` 给了 C4 视图之外的视图（同 `unicode view` 的 `--layer` 和 `--level`），为 400 `serve.bad-parameter`。快照文件在运行中变得读不出时，请求得到 503 `serve.unreadable-snapshot`，文件恢复后照常回答；基准提交建不出图，或者服务端自身失败，为 500 `serve.internal-error`。

### 7.6 评审记录

`review` 组件按内容判断评审是否有效，提供读取、写入、计算候选和生成评审层片段的接口；接口以 `design/review.uc` 为准。记录保存在 `.unicode/reviews/<记录内容的 SHA-256>.json`，版本为 1，每个文件只含一条不可变记录。记录内容的 JSON 对象键逐层按字典序排列，数组保留顺序，编码采用 encoding/json 的 UTF-8 与 HTML 转义规则且无额外空白。记录包含 UTC RFC3339Nano 时间、评审者、目标、内容指纹、结论、意见、执行输入哈希，以及供追溯的提交和 dirty 信息。重复相同记录幂等，不做单一大文件的读取后改写。缺失存储是空集合；版本、字段、时间、哈希或路径不合法，以及符号链接，均给出诊断。

目标恰为节点标识，或 `(edgeKind, from, to)`；二者不混用。普通节点的有效指纹基于 `graph.digest`；边基于身份和属性的 `graph.edgeDigest`，与比较一致，位置属性仍算边内容。人工性质和人工流程的指纹另外包含 `checks` 绑定和手写谓词的内容；带具名观察的性质另外包含观察声明、`observes` 绑定及适配器内容，满足 model.md 第 33、36 条。其他无关内容不泛化传播失效。最新的匹配记录按 `(at, id)` 决定，状态是 `reviewed`；没有匹配记录时为 `pending`。结论与状态分开，评过不等于批准。

无基准时，候选包括当前设计与生成文件之外的代码的节点、边；普通细节函数仍在候选内。带基准时，候选为比较中的新增、修改和删除，并补上自身未变而因手写谓词或观察适配器变化待审的性质。删除目标用墓碑指纹，不能因为当前图里没有它就漏审。写入时重新计算指纹；调用方给出 `expectedDigest` 时，目标已变则拒绝写入。存储的记录不因结论而设置一致性状态。

建图时加入 review 层记录节点和指向仍存在目标的 `about` 边；边目标的完整身份保存在节点属性中，删除项不生成悬空边。查询、评审计算及执行输入哈希排除这些运行产物，避免记录使自身失效。**执行输入哈希** `graph.inputDigest` 是决定执行的那部分图的确定编码的 SHA-256：排除证据层、评审层、用例、生成文件中的代码及其关联边，保留其余节点、边和位置；用例另以它的输入哈希锚定。评审记录保存整张图的执行输入哈希；一条性质或流程的执行输入哈希只编码它的执行范围（[model.md](model.md) §3.5），当前证据和判定的复用都按后者。录制后新增用例及重新生成驱动不会立即使刚产生的证据过期。

命令行写记录，查看器接口仍只读。实体和边的预览使用现有评审位置展示真实状态、结论和意见；待审列表支持比较基准与删除项。`GET /api/reviews` 缺省 pending=true，可给 base 和重复 id 参数；实体和边预览的 review 字段给出当前指纹对应的最新记录，接口定义见 api/reviews.tsp。查看器只读快照（§7.5.1）：写入的记录由下一次 `unicode build` 编进快照之后，在快照改变后的下一次请求中显示，不要求重启服务。界面沿用已有 Figma 原型的评审与证据位置；新增交互须先更新原型。

## 8 命令行

命令行的使用者既是人，也是 agent，约定遵守 cli-design 的规则：标准输出只放数据，诊断和日志写到标准错误；每个命令都支持 `--format text|json`；不读标准输入，不提示确认。

- **全局参数**：`--root DIR` 指定仓库根目录，缺省为向上找到的第一个含 `design/system.uc` 的目录；`--rev REV` 让查询读一个提交的快照，缺省读工作区。
- **退出码**：0 成功；1 未知错误；2 参数错误；3 标识不存在；5 冲突（`gen` 要写的位置已有不同的内容）；7 环境错误（找不到 `python3` 或 Go 工具链）；10 存在诊断；11 有谓词未通过。
- **`check`**：建图并检查全部约束；设计有错时，各阶段照样运行，诊断全部报出。JSON 为 `{"diagnostics": [...], "statuses": {...}}`。代码无法抽取时给出 `cli.extract-failed`，位置在系统文件中该语言的块，退出码为 10；找不到语言的工具链时退出码为 7；尚无后端的语言给出 `cli.unsupported-language` 并跳过。
- **`build`**：建图有诊断时（不含 `check` 的约束）不写快照，退出码为 10；JSON 为 `{"diagnostics": [...], "snapshot": "路径"}`。快照之外，`build` 在同一目录写出 `build.json`，称为 **build 记录**，即 `{"commit": "…", "dirty": false}`：`commit` 是仓库所在提交的完整哈希，`dirty` 表示根目录下有没有未提交的改动或未跟踪的文件，`build` 自己写出的 `graph.json` 和 `build.json` 不算。不在 Git 的工作区中、还没有提交或找不到 `git` 时，写出 `{"commit": null, "dirty": true}`。`build` 还写出 `budget.json`，即每条性质和流程生成的用例数（§6.3 的执行计划）。`--out DIR` 把这些文件写到 `DIR` 中。搜索索引 `index.json` 等查看器确定格式后再写。
- **查询**：`node`、`slice`、`impact` 和 `view` 每次都按工作区重新建图；`--rev REV` 只用于这些查询，以 `git archive` 取出该提交的文件到临时目录。查询中的标识（包括 `--expand` 的）不存在时退出码为 3；视图不适用于输入时退出码为 2。`view architecture`、`view events`、`view ddd` 和 `view c4` 可以不给标识，表示整个系统。`--layer` 只用于类视图，缺省为 `design`；`--level` 只用于 C4 视图，缺省为 `container`；给其他视图这两个参数，或者取值不是这几种，是参数错误。JSON 的字段名是设计中的名称（小驼峰）。
- **`diff`**：`unicode diff <rev>` 像查询的 `--rev` 一样取出 `<rev>` 并建图，与按工作区建出的图比较；带 `--to REV` 时，与 `REV` 的图比较。两张图按 [model.md](model.md) §8 比较（`graph.Compare`）：节点按标识对齐，内容哈希不同为修改；边按种类、起点、终点对齐，属性不同为修改；只列出新增、删除和修改的项。与查询一样，建图的诊断由 `check` 报出，`diff` 不报。JSON 与 `api/compare.tsp` 的 `Comparison` 相同：`{"base": 提交, "head": 提交, "nodes": [...], "edges": [...]}`。提交是 `{commit, short, branch, subject, time}`，`branch` 只在该提交正是检出的分支所在时给出，`time` 是提交时间（UTC）；`head` 另有 `dirty`，与工作区比较时同 `build.json` 的 `dirty`，与提交比较时为 `false`。`nodes` 中每项是 `{id, change, before, after, attrs}`，`change` 为 `added`、`removed` 或 `modified`，`before`、`after` 是两边的节点（与 `node get` 的节点相同），只在该边有它时给出；`attrs` 按键排序，列出两边的值不同的键，每项 `{key, removed, added}` 是该键上去掉和加上的值，按各自原来的次序，重复的值按出现次数计。`edges` 中每项是 `{kind, from, to, change, before, after}`。文本先写两端的提交，再在 `nodes` 和 `edges` 两节中每项一行，修改的节点之后每个变了的键一行。`<rev>` 或 `REV` 不是提交时退出码为 2，找不到 `git` 时为 7。`diff` 不接受 `--rev`。
- **`serve`**：只显示快照中编入的内容，`test` 和 `review record` 写出的结果和评审在下一次 `build` 之后才显示（§7.5.1），这两个命令的帮助说明这一点。`--snapshot` 缺省为根目录下的 `.unicode/graph.json`，`--addr` 缺省为 `127.0.0.1:8765`。`serve` 在 `/` 下提供页面，在 `/api` 下提供接口；`/api` 只接受 GET 和 HEAD，其他方法得到 405。页面缺省是嵌入程序中的前端（§3）。`--web DIR` 改为提供该目录中的文件，供开发前端时使用；给出的不是目录时是参数错误。地址不是页面中的文件时给出 `index.html`，由页面自己读地址的其余部分。程序没有嵌入页面时（不经前端构建、直接 `go build` 得到的程序），只提供接口，并在标准错误中说明，给出修正：用 `make build` 构建，或者用 `--web` 给出构建好的页面。开始监听后，标准输出写出页面的地址（JSON 为 `{"url": …}`），每个请求的日志写到标准错误；收到中断信号时退出，退出码为 0。快照不存在或读不出时退出码为 7，提示先运行 `unicode build`；地址无法监听时退出码也为 7。`serve` 不接受 `--rev`，比较的基准由接口的 `base` 参数给出。
- **`check --design-only`**：解析 `design/` 和 `corpus/` 下的全部文件，报出语法、规范格式和 §5.1 的诊断；JSON 为 `{"diagnostics": [...]}`。M2 之前，不带 `--design-only` 的 `check` 是参数错误。
- **路径参数**：按工作目录解析，必须是根目录下 `design/` 或 `corpus/` 之内的文件或目录。路径不存在、不在这两个目录之内，或者找不到缺省的根目录，都是参数错误。目录会被遍历。`design/` 或 `corpus/` 中 `KindOf` 拒绝的文件给出诊断 `cli.not-a-design-file`，读不出的文件给出 `cli.unreadable-file`，符号链接给出诊断 `cli.symlink`，既不跟随读取，也不改写。全局参数也可以写在命令之后。
- **构建与版本**：`make build` 先构建前端（`pnpm --dir web install --frozen-lockfile`，再 `pnpm --dir web build`），再用 `go build` 构建带页面的 `bin/unicode`。`unicode --version` 在标准输出写出版本（JSON 为 `{"version": …}`），退出码为 0。版本由构建时的 `-ldflags "-X main.version=…"` 写入：`make build` 写入 `git describe --tags --always --dirty` 的结果，`make build VERSION=…` 可以另给；发布的程序写入标签。没有写入时取 Go 记录的模块版本（例如 `go install …@v1.2.3` 得到 `v1.2.3`），再没有时为 `dev`。
- **发布**：推送 `v*` 标签时，`.github/workflows/release.yml` 用 GoReleaser 按 `.goreleaser.yaml` 构建并发布：先构建前端，再为 linux、darwin 和 windows 的 amd64、arm64 构建程序，版本为标签，Windows 打包成 `zip`，其余打包成 `tar.gz`，附 `checksums.txt`。工作流中的各个 action 按提交固定版本，GoReleaser 固定为 v2.20.3。
- **`--traffic`**：`unicode test` 另把 `.unicode/traffic/` 中采集的调用回放为用例（§6.6，[language.md](language.md) E29），带 `--since` 时它们也是版本差分的输入（§6.5）。目录不存在时没有采集的调用；文件不合规范编码、指向不存在的操作或不合该操作的签名时给出诊断，退出码为 10。
- **部署**：使用者部署一个新版本之前按下面的步骤检查它，任何一步失败都不部署：
  1. 把正在运行的版本写出的 `runs/` 和 `traffic/` 放进仓库的 `.unicode/runs/` 和 `.unicode/traffic/`。
  2. 运行 `unicode test --since DEPLOYED --traffic`，`DEPLOYED` 是正在运行的版本构建所在的提交，即它的运行记录和采集的调用中记下的提交。采集的调用回放为用例，版本差分以它们为输入比较 `DEPLOYED` 与要部署的版本；有不通过的结论时退出码为 11，差分有不同时为 10。
  3. 运行 `unicode gen --check`，再以 `go build -tags unicode_monitor` 构建要部署的程序；运行时由 `UNICODE_MONITOR_RATE`、`UNICODE_MONITOR_TRAFFIC`、`UNICODE_MONITOR_DIR`、`UNICODE_MONITOR_KEY` 和 OpenTelemetry 的 `OTEL_*` 环境变量配置（§6.6）。
- **改写与输出**：改写在 POSIX 上是原子的（Windows 上不保证原子），并保留文件的权限，失败时不留下临时文件；写入或输出失败时退出码为 1。`cli.not-canonical` 的位置是与规范格式第一处不同的字节。`--help` 写到标准输出，退出码为 0。JSON 缩进两个空格。带 `--format json` 时，诊断是数据，写在标准输出的 JSON 中，标准错误只放日志；文本模式下，诊断写到标准错误，标准输出只列出改写了的或不是规范格式的文件。
- **诊断的 JSON**：`{code, subject, path, line, column, message, fix}`。`code` 是稳定的诊断码，写作 `<组件>.<短横线名称>`，例如 `syntax.unexpected-token`；每条约束有一个或几个，修正办法不同的子规则各用一个。`subject` 是出错的节点、边或文件；`syntax` 和 `cli` 的诊断，`subject` 是文件的路径。
- **生成的 JSON**：与 `lang.Generation` 同形，为 `{edits: [{path, content, createOnly}], diagnostics: [...]}`；`content` 是 UTF-8 源码字符串，不是字节的 base64。`--dry-run` 返回同样的生成计划，不写文件。有诊断时 `gen` 不写入任何文件；没有诊断时，文本模式只列出生成文件的路径。目标已有文件而没有生成标记时是冲突，退出码为 5。
- **运行的 JSON**：与 `lang.RunReport` 同形，为 `{version, snapshot, commit, dirty, at, venue, mode, results: [{id, passed, accepted, rejected, observations, differences, diagnostics, cases, codeTotal?, branchTotal?, errorTotal?}], diagnostics}`；`venue` 是执行场合（[model.md](model.md) §3.5），`unicode test` 写 `test`。运行时的运行记录（§6.6）与它同形，`venue` 为 `runtime`，没有 `snapshot` 和 `mode`，`accepted` 是适用的调用数，结论另有 `outsideDomain`（各项为不成立的限定或前提 `clause` 和次数 `calls`）、`clauses`（各项为子句 `clause` 和判定的次数 `judged`）、`p95`（以纳秒计）和流程的 `traces`，`cases` 只有反例；cases 保存逐输入的冻结模型值、inputHash、覆盖、轨迹、耗时及结果，数组为空时也输出 `[]`。外层的 `diagnostics` 列出不属于任何一条结论的诊断：工具失败、检查错误（[language.md](language.md) E15）和结果写入失败，有这样的诊断时退出码为 10；工具链不存在仍为 7。外层没有诊断而有 `passed = false` 的结论时退出码为 11，该结论的 `diagnostics` 指出不成立的 `ensure` 或范围外的差异。观察失败可以另列在相关的结论中，但外层的 `diagnostics` 中必须也有。命令输出和 `.unicode/results.json` 均使用小驼峰字段，所有层级的诊断都使用上面的扁平 JSON 形状；`diag.Diagnostic` 的 JSON 编解码统一写成此形状。
- **诊断码与规则**：违反规则的诊断码按规则列在 [language.md](language.md) 和 [model.md](model.md) 的附录 B 中。不属于任何规则的诊断码如下：

  | 诊断码 | 原因 |
  | --- | --- |
  | `cli.unreadable-file` | 文件读不出，属于输入输出 |
  | `cli.symlink` | 符号链接既不跟随读取，也不改写，属于文件系统 |
  | `cli.extract-failed` | 代码无法加载，或源码根目录不存在，属于环境 |
  | `cli.unsupported-language` | 系统文件配置的语言尚无后端，属于工具链的能力 |
  | `cli.record-generation-failed` | 录制后重新建图或生成失败，须重试 unicode gen 恢复当前驱动 |
  | `serve.not-found` | 查看器请求的标识、边、文件或接口不存在，属于请求 |
  | `serve.not-applicable` | 视图不适用于请求的输入，属于请求 |
  | `serve.bad-revision` | 请求的基准提交读不出，属于请求 |
  | `serve.bad-path` | 请求的路径不是快照描述的文件，属于请求 |

  | `gen.symlink` | 生成目标或其父路径是符号链接 |

## 10 工具链对自己的验证

- **静态检查**：`gofmt`、`go vet`、`golangci-lint`，以及 `unicode fmt --check` 和 `unicode check`。`make rule-check`（`scripts/rulecodes.py`）检查每条规则在 [language.md](language.md) 或 [model.md](model.md) 的附录 B 中有一行，这两张表与 §8 的表合起来恰好列出代码中的全部诊断码。M2 之前，组件之间的导入由 golangci-lint 的 depguard 检查；M2 起改由 `unicode check` 按设计中的 `uses` 检查。
- **性质**（M1 时写成带符号的 `property`，M4 起由工具链自己生成驱动）：
  1. `fmt` 幂等。
  2. 规范格式打印之后再解析，得到同一棵语法树。
  3. 解析任何字节都不会 panic；出错时给出诊断，位置在文件之内。
  4. 相同的输入得到逐字节相同的快照，与文件的枚举顺序无关。
  5. 诊断的集合与文件的枚举顺序无关。
  6. `gen` 对骨架只新增：`gen` 之前已有的每个函数体，`gen` 之后逐字节不变；`gen` 两次与一次的结果相同；`gen` 之后不再有 `missing`，只剩 `stub`。
  7. 生成器产生的每个值，都通过与声明的用例相同的类型和限定检查。
  8. 回放录制文件，得到的覆盖与录制时相同；缩减之后的覆盖等于缩减之前的。
  9. `diff(a, a)` 为空；`diff(a, b)` 与 `diff(b, a)` 互为相反。
  10. 推导出的 `depends`、`traces`、`reaches` 与按 [model.md](model.md) §9 的定义直接计算的结果相同；输入是随机生成的小图。
- M4 之前，这些性质的驱动手写，用 `pgregory.net/rapid` 和 Go 原生的 fuzz；M4 起改为生成，手写的驱动随之删除。
- **两个阶段**：开发时只跑 `make check`，随机检查用缺省的次数，几分钟之内结束，通过就提交。深度验证 `make deep` 只在用户同意之后运行：一部分开发完成后，主会话向用户汇报并提议运行，用户同意了才由单独的 agent 在自己的工作区中跑，或者手动触发 CI；随机检查用大的次数，每个 fuzz 目标跑一段时间，再用 gremlins 做变异测试。它不阻塞开发；存活的变异和找到的失败，都成为之后的修复任务。gremlins 的结果要这样读：它只跑被变异的包自己的测试，用缺省的随机检查次数，所以存活的变异要用大的次数再确认一次；编译不过的变异被它算作杀死，要另外剔除；`switch` 的 `case` 表达式没有覆盖的块，其中的变异它不会运行。M6 起，`unicode test --explore` 接替其中的随机检查和 fuzz。

## 附录 A 设计理由

1. **一套结构，多种记法**：DDD、UML、时序图、事件风暴各自的元素，都能归为容器、类型、操作、参与者、流程和性质。把它们统一成一套结构，同一个对象在各种图中自然就是同一个节点；换一种记法只是换一种视图，不用改设计。
2. **两层用同一套种类**：代码层的包、类型和函数，与设计层的容器、类型和操作种类相同。`realizes` 因此是同种类节点之间的对应，比较和视图都可以在两层之间切换。
3. **消息分三种，外部系统只描述接口**：各种通行的记法都区分同步调用、异步消息和事件。UML 时序图用实心箭头和开放箭头区分前两种；BPMN 有消息流和抛出、捕获事件；事件风暴用"每当某事件发生就执行某命令"的策略把事件接到下一个动作；AsyncAPI 用通道上的发送和接收描述事件。外部系统在 C4 中是边界外的软件系统，在 BPMN 中是黑盒的池。我们取它们的共同部分：`call`、`send`、`emit` 加上 `subscribes`，外部系统只写它对我们提供的类型和操作。调用的子步骤对应 UML 的嵌套激活，让静态检查能从具体的那个方法出发去找调用。
4. **有状态的性质用 `call<…>`，不另设状态机语法**：一串调用只是一个列表类型的符号，生成、缩小、用例和录制都沿用同一套机制；`apply` 由生成得到，谓词仍然只是谓词。
5. **检查都是谓词，测试全部生成**：输入都由符号描述，回放、探索、fuzz 和录制才能统一处理；具体的例子写成用例，不另写固定例子的测试。
6. **按覆盖录制，分快慢两条路径**：快路径只回放，确定、迅速，每次修改都能跑；慢路径在预算内扩展输入空间。覆盖给出了"测试好不好"的可度量标准：没有带来新覆盖的输入不保留，反例永远保留。
7. **录制文件进 Git，但不在 `design/` 中**：它们是检查的输入，和种子一样随代码的版本走，任何克隆都能跑同样的快路径。它们由工具写出，放在 `corpus/` 中，不打扰人读设计。
8. **自定义格式，而不是 YAML、JSON、HCL 或 CUE**：签名、流程的步骤和限定各写成一行；只有一种规范写法，diff 干净；语法错误能精确到位置，并说明怎样修正；不接受别的写法，校验才有意义。HCL 和 CUE 都现成带有解析和格式化，CUE 还能校验值与类型和限定是否相符；但流程在 HCL 中要写成层层的块，在 CUE 中是嵌套的结构体列表，同一个意思又有多种写法。用 participle 之后，自己写的只剩语法定义、语法之外的规则和打印，代价小于流程变得难读。
9. **只有错误，没有警告**：警告会被忽略。只要有一处违反留下来，agent 就会把它当成惯例去复制。
10. **代码只细到函数**：字段和变量太多，人记不住，设计也不需要一一对应到它们。
11. **绑定只写在类型和自由函数上**：方法按固定的名称映射对应到操作，不必在每个方法上再写一遍标识；生成和检查都按同一套映射进行。
12. **静态抽取**：不运行代码就能建图，又快又确定，也不需要运行环境。执行得到的证据由 `unicode test` 和受监控的程序（§6.6）产生，作为证据并入。
13. **显著性由设计决定**：人写进设计的就是他要关注的。不另设一套标注，就不会出现标注与设计不一致。关注度只用来把整个支撑容器或工具容器折叠起来。
14. **取值域只写一处**：符号的类型和限定写在设计中，生成器、fuzz 的解码和用例的检查都由它推出。用例只给输入，结果由谓词判断，所以用例是性质的实例，而不是另一份测试。
15. **骨架与生成文件分开**：骨架生成之后归人所有，`gen` 不改写它，人写的函数体因此不会丢失；生成器和驱动完全由设计决定，归 `gen` 所有，每次重写，并由检查确认与设计一致。
16. **先做 Go 后端**：工具链用 Go 写，Go 后端做好后，工具链立刻能检查自己，每一步都有真实的反馈。
17. **快照不进 Git**：快照是生成物，随时可以从提交重建；Git 只保存设计文件、录制文件和代码。
18. **工具链不调度 agent**：调度由使用工具链的设计者负责。工具链只做设计、生成、检查、运行和查询，接口因此简单而确定。
19. **优先用维护中的外部库**：库的代码有人维护，我们只维护怎样用它，评审时也只需看用法；精力放在性质所描述的整体行为上，而不是细节的打磨。
20. **规则对照表的检查用 Python 写**：仓库中的每个 Go 文件都归属于设计中的某个组件，`scripts/rulecodes.py` 只读文档、设计文件和源码，不属于任何组件，所以不用 Go 写；它只用标准库。
21. **缓存按内容，判定按键复用**：`make check` 的大部分时间花在没有缓存的抽取上，`check`、`gen --check` 和 CLI 的性质每次都重新加载全部的包；缓存的键都由内容哈希组成，内容不变就不重做，不依赖时间或提交。判定以性质的执行范围为键，而不以整张图为键，否则改动任何一处都会让全部证据过期。模板不用硬链接：经硬链接原地写入会改动模板，模板只读又会让本来能写入的用例失败。
22. **运行时经接口包装，不改写代码**：Go 不改动调用处就截不住一次直接调用。测试中可以在内存中给源码插桩（§6.4），部署的程序却应当就是评审过的源码编出的。接口是组合根本来就掌握的接缝，接口包装就写在这里，业务代码不变；不经接口的函数只在入口包装，因为入口的函数值同样由组合根交出去。
23. **监控文件带构建条件**：默认构建不含监控文件，`monitor.Wrap` 和 `monitor.Entry` 原样返回参数，程序的行为和开销与没有监控时相同；组合根在两种构建中是同一份源码，打开监控只是换一个构建条件。
24. **判定深度和廉价都由效果推出**：效果（[model.md](model.md) §9 D8）已经是执行计划估计耗时的依据（§6.3），读文件、进程或网络的操作和适配器本来就慢，每次真实的调用再读一遍状态，开销和风险都落在用户身上。由效果推出不需要新的语法，也不会与代码不符：适配器改成读文件，它就不再廉价。
25. **运行时的结论按提交求执行输入哈希**：部署的程序中没有图，求不出执行输入哈希；把哈希写进监控文件，则改动执行范围中任何一个函数体都要重新生成，`unicode gen --check` 会频繁失败。程序的构建信息已经带着提交，`build` 按提交建图求哈希，每个提交只建一次。
26. **脱敏用带密钥的摘要，在回放时由生成器补值**：采集和反例的记录离开了程序，可能被提交、转交或长期保存，所以敏感的值不能以原样写出。带密钥的摘要保留相等关系（例如两次输入的口令相同），没有密钥就无法验证猜测；回放需要该类型的一个值，由生成器以摘要为随机源取得，确定而不泄露原值。敏感的数据取一个自己的具名类型，例如值对象 `Password` 或 `Email`，标签加在这个类型上，脱敏就随类型到达它的值出现的每一处：字段、实参、集合的元素和错误的数据。
