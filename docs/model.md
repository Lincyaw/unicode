# 图模型

一个仓库在一个提交上的全部知识是一张图，称为该提交的**快照**。设计文件、代码、代码中的绑定和录制的用例是图的来源；追溯、索引、视图和分析都是这张图上的查询。本文定义图的统一结构、节点、边、记法、共有的属性、身份和版本，以及图必须满足的约束。设计文件的写法见 [format.md](format.md)，工具链如何建图、生成代码和运行检查见 [design.md](design.md)。

## 1 统一结构

图由四样东西组成：

- **元素**：有名字、有边界的东西，构成一棵包含树。元素只有四个种类：`container`（边界）、`type`（数据的形状，可以带操作）、`op`（可调用的行为）和 `actor`（系统之外的参与者）。
- **关系**：元素之间带种类的边，例如包含、依赖、引用、继承、实现、调用、订阅和落实。
- **流程**：一组按次序组合的步骤：同步调用、异步发送、发布事件，以及分支、可选、循环和错误处理。
- **性质**：关于元素或流程的一条可执行的陈述。

性质和流程都可以声明**符号**，也就是它们的输入。用例就是用这些符号写成的。

同一套种类用于两个抽象层：**设计层**是声明的意图，**代码层**是从代码抽取的事实。代码中的包和文件是 `container`，类和结构体是 `type`，函数和方法是 `op`。`realizes` 边把代码层的元素对到设计层中同一种类的元素上，两层因此可以逐个比较。

DDD、UML 类图、时序图、活动图、事件风暴和 C4 都是**记法**。一种记法从图中选取一部分，按自己的规则画出来；有的记法还给元素加上自己的标签，例如 DDD 的"聚合"。记法不增加结构，也不改变约束，见第 5 节。

此外，图中还有两类附加的节点：证据和评审记录。

## 2 来源

每个节点和每条边恰有一种**来源**：

- **声明**：设计文件写出的，或代码中的绑定写出的。
- **抽取**：语言后端从代码中静态读出的，不执行代码。
- **推导**：由其他节点和边按第 9 节的规则算出的。
- **运行**：执行检查时产生的，包括录制下来的用例。

声明是意图，抽取是事实，推导把二者连起来。第 10 节的约束比较意图与事实，结果写在声明项的状态上。

## 3 节点

每个节点有**种类**和**形式**：种类是下表中的一行，形式是该种类之下更具体的一类。

| 种类 | 设计层的形式 | 代码层的形式 | 属性 |
| --- | --- | --- | --- |
| `container` | `system`（根，恰有一个）、`component` | `package`、`file` | 名称、摘要、关注度、标签；设计层另有拥有的路径，代码层另有语言和路径 |
| `type` | `object`、`record`、`interface`、`enum`、`error`、`event` | 各语言的命名类型，例如 `class`、`struct`、`interface` | 名称、摘要、标签、字段、枚举值 |
| `op` | `op` | `func`、`method`、`abstract`（接口中声明的方法） | 名称、摘要、签名、订阅的事件；代码层另有测试类别、是否为骨架 |
| `actor` | `person`、`external` | — | 名称、摘要 |
| `flow` | `flow` | — | 名称、摘要、符号、限定 |
| `step` | `call`、`send`、`emit`、`async`、`alt`、`opt`、`loop`、`on` | — | 序号、分支标签、实参 |
| `property` | `invariant`、`postcondition`、`relation`、`transition` | — | 名称、陈述、符号、限定 |
| `case` | `declared`、`recorded` | — | 名称、摘要、每个符号的取值；录制的用例另有录制原因 |

### 3.1 元素

- **设计层的 `type`**：
  - `object` 有状态和行为，`record` 只有数据；
  - `interface` 只有操作，`enum` 只有枚举值；
  - `error` 可以出现在操作的 `raises` 中；
  - `event` 是可以发布的数据，操作可以订阅它。
- **字段和枚举值**是 `type` 的属性，不是节点。字段的类型引用另一个 `type` 时，得到一条 `refers` 边。代码层只细到函数：变量和局部定义都不是节点。
- **`op`** 可以订阅一个事件，表示每当这个事件发布时，它就被调用一次。
- **`actor`**：`person` 是人，只能发起调用。`external` 是外部系统，可以包含类型和操作，用来描述我们用到的它的接口。外部系统在本仓库中没有自己的代码；落实它的类型和操作的，是我们的客户端代码。
- **关注度**是设计层 `container` 的属性，取值为 `core`（核心）、`support`（支撑）或 `utility`（工具与基础服务）。它决定视图默认展开到哪里（[design.md](design.md) §7.2），不改变约束。
- **代码层的 `op`**：签名由语言后端归一化成与语言无关的形式（[design.md](design.md) §4）。测试类别是 `none`、`example`、`property` 或 `fuzz`，由后端按该语言的测试约定判定。是否为骨架，指函数体是否恰好是 `gen` 生成的未实现标记。

### 3.2 流程

流程的步骤构成一棵树：

- **`call`**：同步调用，发起方等待它返回。调用可以带子步骤，表示接收方在这次调用中做的事，即 UML 时序图中的一段激活。
- **`send`**：异步调用，发起方不等待。经过消息队列或总线的异步，写成事件。
- **`emit`**：发布一个事件。接收方由订阅关系决定，发起方不知道有谁接收。
- **`async`**：订阅者收到此前发布的事件（或此前发送的调用）之后做的事。
- **`alt`、`opt`、`loop`**：分支、可选和循环片段。
- **`on`**：前一次调用抛出某个错误时的分支。

流程可以像性质一样声明符号和限定，它们就是流程的输入；流程的检查用这些输入走一遍流程。

### 3.3 性质、符号与用例

- **性质的形式**：
  - `invariant`：对每个取值或状态成立；
  - `postcondition`：在操作返回后成立；
  - `relation`：在几次调用的结果之间成立，例如往返、幂等、变形关系；
  - `transition`：状态只按允许的转移变化。
- **符号**：有名称和设计中的类型。性质的陈述对符号的每一组取值都成立。符号的类型可以是 `call<R1, …>`，它的一个值就是对 R1, … 中某个操作的一次调用，带全部实参；R 是类型时指它的全部操作。有状态的性质因此写成一串调用：`forall steps: list<call<Stock>>`。谓词依次执行这些调用，并在每一步之后检查陈述。
- **限定**：缩小符号的取值范围，例如数值的区间、集合的大小、枚举的子集。一个符号的**取值域**，是它的类型的全部取值再按它的限定缩小后的部分。
- **生成的符号**：有的取值域写不成类型和限定，例如"一段合法的设计文件文本"。这样的符号标为 `generated`，附一句话说明它的取值域；它的生成器由代码中的 `generates` 绑定给出（[format.md](format.md) §4），它不带限定。
- **用例**：为每个符号给出一个具体的值，必须落在取值域之内。用例只给输入，不给期望结果，结果由检查判断。用例分两种：
  - **声明的用例**写在设计文件中；
  - **录制的用例**由探索挑选出来，写在录制文件中（[design.md](design.md) §6.3）。录制的原因是 `coverage`（它增加了覆盖）或 `counterexample`（它是缩小后的反例）。

### 3.4 证据与评审记录

- **证据**：
  - `run` 是在一个提交上执行一组检查的一次运行；`result` 是一个检查在一次运行中的结论。
  - 运行中由生成器产生、但没有录制的输入，不进入快照。
  - 每个用例覆盖到的代码和设计，记为 `covers` 边。
- **评审记录**（M7）：`review` 记下谁在哪个快照上评审了哪个节点或哪条边、当时它的摘要、结论和意见。评审记录不放在 Git 中，存放的位置在 M7 决定。

## 4 边

| 种类 | 从 → 到 | 来源 | 含义 |
| --- | --- | --- | --- |
| `contains` | container → container、type、op、flow、property；system → actor；actor → type、op；type → op；flow → step；step → step；property、flow → case | 声明；抽取；运行 | 包含，每层各构成一棵树 |
| `uses` | container → container、actor | 声明 | 允许的依赖 |
| `extends` | type → type | 声明；抽取 | 继承或嵌入 |
| `implements` | type → type | 声明；抽取 | 实现接口 |
| `refers` | type → type；op → type；property、flow → type | 声明；抽取 | 字段、参数、返回值、错误或符号引用的类型；代码层的 op 另有函数体中构造或使用的类型 |
| `subscribes` | op → type | 声明 | 操作订阅的事件 |
| `imports` | container → container | 抽取 | 文件导入包 |
| `calls` | op → op | 抽取 | 静态解析到的调用；属性中列出每个调用位置 |
| `calls` | step → op | 声明 | `call`、`send` 和 `async` 步骤指向的操作；接收方是该操作所属的类型、容器或外部系统 |
| `from` | step → actor、container、type | 声明 | 步骤的发起方 |
| `emits` | step → type | 声明 | `emit` 步骤发布的事件 |
| `handles` | step → type | 声明 | `on` 片段处理的错误 |
| `about` | property → container、type、op、flow | 声明 | 性质约束的对象 |
| `realizes` | 代码层 type → 设计层 type；代码层 op → 设计层 op | 声明（代码中的绑定）；推导 | 代码元素落实设计元素：类型和自由函数由绑定写出，方法由名称映射推出（第 9 节） |
| `checks` | 代码层 op → property、flow | 声明（代码中的绑定） | 这个谓词检查该性质或流程 |
| `generates` | 代码层 op → property、flow | 声明（代码中的绑定） | 这个函数给出该性质或流程的一个生成的符号的生成器；属性中写明符号的名称 |
| `owns` | 设计层 container → 代码层 file | 推导 | 文件归属的容器 |
| `depends` | 设计层 container → 设计层 container、actor | 推导 | 实际的依赖 |
| `traces` | step → 代码层 op | 推导 | 落实该步骤所调用操作的函数 |
| `exercises` | 代码层 op → 代码层 op | 推导 | 谓词沿静态调用可达的函数 |
| `reaches` | 代码层 op → 代码层 op | 推导 | 两个显著函数之间只经过细节函数的调用；属性列出经过的函数 |
| `covers` | case → 代码层 op；case → step | 运行 | 用例执行到的函数（属性中列出行）和走到的步骤 |

## 5 记法与标签

记法分两类：

- **投影**只用结构，不需要标签：
  - 架构图画容器和依赖；
  - UML 类图画类型、字段、操作及其关系；
  - 时序图按发起方和接收方分出生命线画流程，同步调用画实心箭头，发送画开放箭头，发布画到事件，订阅者的激活画在之后；
  - 活动图按步骤的控制结构画同一个流程；
  - 事件图画事件、发布它的步骤和订阅它的操作，也就是事件风暴的大图；
  - 调用图画函数之间的调用。
- **带标签的记法**为元素加上记法自己的词汇，再按词汇选取和画出。

标签的词汇由工具链内置，是固定的。系统文件用 `notation` 声明项目使用哪些记法，元素只能带这些记法的标签；每个标签规定它能用在哪种元素上。第一版内置两套词汇：

| 记法 | 标签 | 用于 |
| --- | --- | --- |
| `ddd` | `bounded-context` | container |
| `ddd` | `aggregate`、`entity`、`value`、`domain-service`、`repository`、`factory` | type |
| `c4` | `software-system`、`container`、`component` | container |

领域事件不用标签：形式为 `event` 的类型就是事件。标签只影响视图，不影响约束。带标签的记法各有一个视图（[design.md](design.md) §7.1）。

## 6 共有属性

每个节点和每条边都有：

- **标识**：见第 7 节。
- **种类**、**形式**和**层**。
- **来源**：见第 2 节。
- **出处**：写出它的位置，即设计文件、录制文件或代码文件的路径和行号；推导项的出处是推出它的那些边。
- **摘要**：它自身内容的 SHA-256，不含子节点，用来判断它变了没有。节点的内容是它的种类、形式、摘要和属性（[design.md](design.md) §5.2），按确定的方式编码；代码层的 `op` 另含归一化后的函数体，代码层的 `type` 另含不含方法体的声明。
- **显著性**：显著，或是细节，见第 9 节。
- **状态**：只有声明项才有状态，取值为 `verified`（与代码一致）、`missing`（代码中没有对应项）、`stub`（对应的函数还是骨架）或 `contradicted`（代码与声明不符）。状态由第 10 节的约束算出。

## 7 身份

- **设计节点**的标识按包含关系逐段写出，段与段之间用 `.` 连接。例如：
  - 容器：`order`、`order.pricing`；
  - 类型：`order.Order`；
  - 操作：`order.Order.total`；容器直接提供的操作为 `order.parseCart`；外部系统的操作为 `payment-gateway.charge`；
  - 流程和性质：`order.submit-order`、`order.total-is-sum`；
  - 符号：`order.total-is-sum.order`，只在 `generates` 绑定中使用；
  - 用例：`order.total-is-sum.empty`，录制的用例名为 `r-` 后接其取值摘要的前 8 位十六进制，例如 `order.total-is-sum.r-3f9a2c1d`；
  - 系统：系统的名称，例如 `shop`；参与者和顶层容器因此不能与系统同名；
  - 参与者：`customer`；
  - 步骤：流程的标识后接 `#` 和它在流程中按文本先后的序号，从 1 起，子步骤和片段中的步骤也计入，例如 `order.submit-order#3`。
- **代码节点**的标识带语言前缀：包为 `go:github.com/x/shop/order`；类型为 `go:github.com/x/shop/order.Order`；方法为 `go:github.com/x/shop/order.Order.Total`；Python 的方法为 `py:shop.order.Order.total`；文件为 `file:src/shop/order.py`。
- **边**的标识是（种类，起点，终点）。同一对函数之间有多处调用时，只有一条 `calls` 边，调用位置都列在它的属性中。
- 改名或移动算作删除旧节点、新增新节点。工具可以提示可能的改名，但不会自动把两者认作同一个节点。

## 8 快照与比较

- 快照是一个提交或一个工作区的图。序列化的结果是确定的：节点和边按标识排序，相同的输入总是产生逐字节相同的输出。
- 比较两个快照时，按标识对齐节点和边，每一项归为新增、删除、修改（摘要不同）或不变。
- 评审状态由比较算出：一项从未审过，或审过之后摘要变了，就是待审。

## 9 推导规则

- **`owns`**：一个源文件归属于路径模式匹配它的设计层容器中最深的那个。
- **方法的 `realizes`**：代码层类型 c `realizes` 设计层类型 t 时，t 的每个操作 o 由 c 中名为 o 的名称映射（[design.md](design.md) §4）的方法落实，得到 `realizes` 边。接口中声明的方法也是 `op` 节点，形式为 `abstract`；经由接口的调用，`calls` 边指向它。
- **`depends`**：容器 A 拥有的某个文件导入了容器 B 拥有其文件的包，或者 A 拥有的某个函数调用了 B 拥有的某个函数，且 A ≠ B 时，有 `depends` A → B。A 拥有的函数调用了落实外部系统 X 的操作的客户端时，有 `depends` A → X。边的属性列出这些导入和调用，作为依据。
- **`traces`**：`call` 或 `send` 步骤 s `calls` 设计层操作 o，而代码层操作 f `realizes` o 时，有 `traces` s → f。
- **`exercises`**：从 `checks` 边的起点出发，沿 `calls` 能到达的每个函数 g，都有 `exercises` 边到 g。
- **显著性**：
  - 设计层的节点都是显著的。
  - 在代码层中，落实设计节点的类型和函数（包括按名称映射落实操作的方法）是显著的，谓词和带 `generates` 绑定的生成器也是显著的，其余的类型和函数是细节。
  - 含有显著元素的文件和包是显著的；`gen` 产生的生成文件中的元素都是细节。

  人在设计中写下的就是他要关注的，所以显著性由设计决定，不需要另外标注。
- **`reaches`**：显著的函数 f 经由一个或多个细节函数调用到显著的函数 g 时，有 `reaches` f → g，属性列出每条这样的路径上经过的细节函数。f 直接调用 g 时只有 `calls`，没有 `reaches`。

## 10 约束

违反约束得到诊断。诊断一律是错误，没有警告。每条诊断都写明违反了哪条约束、在哪里、怎样修正。下文的容器、类型和操作，未注明层的都指设计层。

**设计内部**

1. 每个引用都能解析到声明的节点，种类与引用的位置相符。
2. 同一个父节点下，子节点的名称互不相同；参与者与顶层容器的名称也互不相同；同一条性质或同一个流程中，符号与用例的名称也互不相同。
3. `contains` 构成一棵以 `system` 为根的树。
4. 跨容器的类型引用，即字段、参数、返回值、错误、订阅的事件、`extends` 和 `implements` 所引用的类型，只能指向允许依赖的容器或外部系统（第 13 条）。
5. 元素的标签属于系统文件声明的记法，并且这个标签能用在这种元素上（第 5 节）。
6. 订阅事件 E 的操作恰有一个参数，参数的类型为 E，E 的形式为 `event`。

**流程**

7. `call` 和 `send` 步骤：
   - 发起方是参与者、容器或类型，人只能是最外层步骤的发起方；
   - 被调用操作所在的容器或外部系统，或者就是发起方所在的容器，或者是它允许依赖的（第 13 条）；
   - 实参的个数等于操作的参数个数。
8. 调用的子步骤，发起方是这次调用的接收方。
9. `emit` 步骤的发起方是容器或类型，发布的类型的形式为 `event`，实参的个数等于事件的字段个数。
10. `on E` 紧跟在一个 `call` 步骤之后，E 在被调用操作的 `raises` 中。
11. `async X.o` 片段：o 订阅了流程中在它之前发布的某个事件，或者是在它之前某个 `send` 步骤调用的操作；片段中步骤的发起方是 o 的接收方 X。

**归属与依赖**

12. 每种已配置的语言，其源码根目录下的每个源文件都恰好归属于一个容器；互不嵌套的两个容器，路径模式不能匹配同一个文件。
13. A 可以依赖 B，当且仅当 B 是 A 的子容器，或者 A 或 A 的某个祖先 `uses` B；B 可以是外部系统。B 的子容器不随 B 一起被允许，要依赖它们须另写 `uses`。
14. 每条 `depends` 都是允许的依赖，否则 `depends` 的状态为 `contradicted`。

**绑定**

15. 绑定指向存在的设计节点，种类相符：
    - 代码层类型的 `realizes` 只指向类型；
    - 不属于任何类型的代码层操作，其 `realizes` 只指向容器或外部系统直接提供的操作；
    - `checks` 只指向 `property` 或 `flow`，一个函数至多带一个 `checks`；
    - `generates` 只指向生成的符号；
    - 方法上不写 `realizes`。
16. 每个类型和每个操作，包括外部系统的，都恰好被一个代码层元素落实。没有时状态为 `missing`；落实操作的函数还是骨架时，状态为 `stub`。
17. 落实设计节点的代码元素，所在的文件归属于该设计节点所在的容器。外部系统的类型和操作，由 `uses` 该外部系统的某个容器中的客户端代码落实。
18. 代码元素的名称是它所落实的设计节点名称的映射，归一化后的签名与设计一致，否则状态为 `contradicted`。比较签名时比较参数的类型与次序、返回值和错误，不比较参数名：参数名是给人读的说明，各语言的习惯（例如 Go 中参数不能遮住包名）常常要求换一个名字。设计中写出的字段，代码层类型都必须有，类型一致；设计之外的字段和方法是细节，可以存在。枚举不同：代码层类型的枚举值与设计中的完全相同，多出的值是设计没有声明的状态，也是 `contradicted`。
19. 类型之间的 `implements` 和 `extends`，在落实它们的代码层类型之间也成立。

**可执行**

20. 每条 `property` 和每个 `flow` 都恰有一个 `checks` 绑定，绑定的函数是**谓词**：除了语言要求的测试句柄（[design.md](design.md) §4），参数恰好是它的符号（可以没有符号），按名称映射，类型一致。
21. 生成文件之外的代码中没有测试函数：测试都是 `gen` 生成的驱动，人写的只有谓词和谓词调用的代码。
22. 每个 `call` 和 `send` 步骤 s 都有 `traces` s → f，并且 f 在代码中可达：
    - s 是某次调用的子步骤时，落实那次调用的操作的函数，要沿 `calls` 能到达 f；
    - s 在最外层、发起方是类型或容器时，落实发起方的代码中（类型的方法，或容器拥有的函数）要有函数能到达 f；
    - 发起方是人时不检查。

    接口中的 `abstract` 方法本身不调用任何函数，所以涉及接口时按分派检查：调用的是接口的操作时，这次调用的子步骤改从实现该接口的代码类型中同名的方法出发；发起方是接口类型时，改从实现它的各个代码类型的方法出发；有一个能到达就满足。

    `emit` 步骤要求发起方的落实代码 `refers` 落实该事件的代码层类型。不满足时，步骤的状态为 `missing`。调用的先后顺序和事件的投递，由流程的驱动在运行时核对（[design.md](design.md) §6.3）。

**符号与用例**

23. 不是生成的符号，其类型必须能够生成：不是 `interface` 或 `error`，也不经由必填字段递归引用自身；`call<…>` 中各操作的参数都能生成，操作名互不相同。
24. 每个生成的符号恰有一个 `generates` 绑定，并且不带限定；不是生成的符号没有 `generates` 绑定。
25. 限定的路径从一个符号出发，逐段解析：
    - 经过 `list`、`set` 时，作用于每个元素；
    - 经过 `map` 时，作用于每个值；
    - 经过 `call` 时，下一段是操作名，再下一段是参数名。

    区间只用于 `int` 和 `float`，枚举子集只用于 `enum`，大小只用于 `list`、`set`、`map`、`string` 和 `bytes`。
26. 用例，包括声明的和录制的，为每个符号恰好给出一个值。值必须符合符号的类型：记录给出全部字段，枚举值存在，只有 `optional` 才能取 `none`，调用给出该操作的全部参数。值还必须满足全部限定。
27. 声明的用例的名称不能是录制用例的名称形式，即 `r-` 后接 8 位十六进制。

**生成与录制**

28. 每个生成文件（[design.md](design.md) §6.2）都与 `unicode gen` 按当前的设计产生的内容逐字节相同。
29. 每个录制文件都指向一个存在的性质或流程，内容是规范格式。

**名称映射**

30. 按每种已配置语言的名称映射（[design.md](design.md) §4）换算之后，同一个容器中类型、操作、谓词和生成器的代码名称互不相同；同一个类型中字段与操作的代码名称也互不相同。例如在 Go 中，类型 `Slice` 和操作 `slice` 都映射成 `Slice`，不能放在同一个容器中。名称映射还必须能往返：映射之后再反向映射，要得到原来的名称；因此性质的名称不能以 `flow-` 开头（否则谓词与流程的谓词无法区分），性质和流程的名称中短横线之后也不能紧跟数字。
